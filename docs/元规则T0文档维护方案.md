### 1.3 核心痛点（本方案要解决的四件事）

1. **块 ID 不稳定**：`rule_section_%02d` / `faq_%02d` 为全局顺序编号。
   中间插入新小节或新 FAQ → 后续所有块 ID 顺移 → 旧块全部失效、索引全量重建、审计记录错乱。
2. **解析器静默丢行**：FAQ 行要求两列内容不含 `|`，术语名有长度/黑名单限制；
   人工编辑格式走样时**悄悄丢失**，脚本不报警（块数校验只能发现总数变化，发现不了"丢的是哪条"）。
3. **确认机制是一次性的**：当前"整合 → 逐条确认 → 定稿"只发生了一次；
   若大更新时整篇重新整合，已确认条目会被 LLM 改写（表述回归），且逐条重确认成本爆炸。
4. **变更入口不闭环**：官方更新 → 数据层自动变化，但"什么情况必须动 T0 文档"没有强制判定机制，
   新机制容易漏进元规则（周更手册已有提示，但依赖人自觉）。

## 2. 总体思路：从"一次性整合"到"增量演化"

T0 文档定位为**只增不改语义的权威版本库**：

- **新增**：新条目（新术语/新状态/新时机/新 FAQ）一律**追加**到语义所属章节的**末尾**，不插入中间；
- **修订**：已确认条目只做"旧值 → 新值 + 依据 + 日期"的修订记录，**不删除原文语义**（废弃条目划线保留）；
- **确认**：任何新条目先落 `[待确认]`，经提案-确认流程后转为 `[已确认(日期,依据)]`；
- **机器守门**：文档格式是解析器的"契约"，改动后必须通过结构校验（见第 6 节），否则拒绝合入。

一句话：**文档只增不删、编号只加不回、确认留痕、机器校验**。

## 3. 变更分流：什么情况需要动 T0 文档

官方每次更新后，先做分流判定（周更手册步骤 2 的 diff 清单扩展"T0 判定"列）：

| 变更类型 | 例子 | 动数据语料 | 动 T0 文档 | 动作 |
|---|---|---|---|---|
| 纯数值微调 | 体力/手牌上限/伤害数值 | ✅ 重跑 | 否 | 仅当 FAQ 引用该数值时修订该条 |
| 技能描述改写（时机不变） | 措辞调整 | ✅ 重跑 | 通常否 | 核对无新时机/新术语即放行 |
| 新增武将（复用既有机制） | 新武将用已知时机/状态 | ✅ 重跑 | 否 | 语料覆盖即可 |
| 新增武将（含新机制） | 新时机/新牌型/新资源/新区域/新状态 | ✅ 重跑 | **✅ 必动** | 走提案-确认流程（第 5 节） |
| 新术语 / 新动作动词 | 官方文案出现未定义动词 | — | **✅ 必动** | 术语表追加条目 |
| 既有规则被推翻 | 公告/实战裁定与文档冲突 | — | **✅ 必动** | FAQ 追加"新裁定优先"条目 + 修订来源条 |
| 组合结算盲点 | 实战/测试答不出的组合 | — | 可能 | 记入疑难登记（第 8 节），消化为 FAQ |
| 武将下架/改名 | 从 heroes.json 消失 | ✅ 标记停用 | 否 | 交叉引用校验报警（第 6 节） |

判定口诀：**"是否引入文档中没有的 时机/状态/术语/资源/区域/牌型/动作，或推翻既有裁定"——有一个"是"，就动 T0。**

## 4. 增量修改协议（文档结构纪律）

### 4.1 章节结构冻结

- 现有章节编号（0~7）与语义**永久绑定，不重编号、不改标题**（标题 = 切块边界，改标题即改块身份）。
- 新内容只能落在两种位置：
  1. **已有小节末尾追加**（表格加行 / 列表加项）——最优，块内容变化但 ID 不变；
  2. **章节内新增 `###` 小节**（追加在本章最后，如 `### 4.11 新机制 X`）——ID 顺移仅限本章内后续小节，可接受；
- 禁止：在文档中部插入小节、重排小节、修改既有小节标题。

### 4.2 块 ID 稳定化（已实施，2026-08-15 改造 build_rule_corpus.py）

| 块类型 | 现状 | 建议 | 理由 |
|---|---|---|---|
| 章节块 | `rule_section_%02d` 全局顺序 | `rule_section_<章号>_<节序号>`（如 `rule_section_04_08`） | 插入只影响本章内后续块 |
| FAQ | `faq_%03d` 绑定裁定编号 | **编号单调递增、不回收**：新裁定接最大编号+1；废弃条目划线保留编号 | 永不冲突、永不顺移 |
| 术语 | `term_<名称>` | 保持 | 天然稳定；改名 = 删旧增新，可接受 |

> 迁移状态：2026-08-15 已完成一次性改造并全量重建（`maintain_rag.py --force`），此后永久受益；
> 期望块数已由 maintain_rag.py 硬编码改为 `.rule_doc_snapshot.json` 快照驱动（只增视为 OK、减少视为失败）。

### 4.3 来源列标准化

「来源」列统一格式：`出处类型 对象`，其中出处类型 ∈ {卡牌, 武将, 点数表, 装备属性表, 数据统计, 人工确认, 公告}，
对象尽量落到可校验的 id（卡牌编号 / 武将名 / 日期）。

- 新增规则强制带来源；来源不明 → 只能标 `[推断]` 或 `[待确认]`，不得标已确认。
- 交叉引用可被机器校验（第 6 节）：引用"武将 郭解"而 heroes.json 已无郭解 → 报警。

### 4.4 更新记录结构化

现状：头部一段连续流水文本（越长越难读、无法机器解析）。

改造为**变更日志表**（放文档末尾附录，或独立 `docs/changelog/元规则changelog.md`，文档头部只留最近一次指针）：

```
| 日期 | 变更对象(块ID) | 类型(新增/修订/废弃) | 旧值→新值摘要 | 依据 | 确认状态 |
```

- changelog 本身是高价值语料（"本周规则改了什么"直接命中），可另行切块入 RAG（周更手册步骤 6 已有此思想）。
- 版本号：沿用 6.1/6.2 建议，以"确认日期 + 序号"为条目版本，如 `R-2026-08-15-01`。

## 5. 提案-确认流程（人机协同，替代"整篇重整合"）

核心：**LLM 只产"变更提案"，不直接改定稿**；人逐条确认后由人（或确认后的脚本）合入。

```
官方公告 + 新数据 diff 清单（含"是否新机制"标记）
   ↓
[1] Codex/LLM 生成《变更提案单》（工作产物，不进 RAG）
      每条提案：类型(新增/修订/废弃) | 目标位置(章/节/FAQ号) | 建议文本 | 依据(公告/数据/实战) | 建议确认状态
   ↓
[2] 人工逐条审阅：通过 / 驳回 / 改写（一次只审变更项，5~20 条，量可控）
   ↓
[3] 合入定稿：按第 4 节协议落位（追加、编号接续、来源标准化、标 [待确认] 或 [已确认(日期,依据)]）
   ↓
[4] 机器校验（第 6 节）→ maintain_rag.py --force（元规则任务）→ 重建索引
   ↓
[5] 回归测试（第 7 节）：确认旧 FAQ 答案不变、新裁定答对
```

### 5.1 确认状态机

```
[推断]（统计/推导，无权威依据）
   ↓ 人工核对
[待确认]（有依据但未逐条核实）── 可进入语料但回答时声明"待确认"
   ↓ 逐条确认（人）
[已确认(日期,依据)]（权威，默认状态）
   ↓ 被新公告推翻
[已修订(日期,依据)]（旧值划线保留，新值追加，FAQ 上"新裁定优先"）
```

### 5.2 防回归纪律（最关键）

- **已确认条目的文本，未经"修订"流程不得改写**；LLM 任何轮次（含整篇重读、摘要、其他任务）不得静默改动。
- 执行方式：git 保护 + 校验脚本比对"已确认区块指纹"（第 6 节），非修订操作改变已确认文本 → 校验失败。
- 待确认清单（第 7 章）与 FAQ 相互引用时，划掉一项必须同步 FAQ 标注，反之亦然（一致性校验项）。

## 6. 机器校验契约（`scripts/audit_rule_doc.py`，已新增）

在 maintain_rag.py 的元规则任务前加一道"文档校验"，失败即中止（`--strict` 可进 CI/pre-commit）：

| 校验项 | 内容 | 防什么 |
|---|---|---|
| 解析回声 | 每个 FAQ 行/术语行都被解析到；解析器丢弃的表格行**逐行报警**（含行号） | 静默丢行 |
| 表格结构 | 每行 `|` 列数一致；内容不含裸 `|`（解析器限制） | 格式走样 |
| 块 ID 唯一 | section/faq/term 块 ID 无重复、无跳号冲突 | 索引冲突 |
| ID 稳定性 | 与上次快照对比：新增 ID 只允许出现在"章节末尾追加位"；中部插入/重排/标题改动 → 警告并列出受影响 ID | 块顺移 |
| FAQ 编号 | 单调递增、无重复；废弃条目必须划线保留编号 | 编号回收 |
| 确认状态一致性 | `[待确认]` 计数变化报告；`~~划掉~~` 条目与 FAQ 标注同步检查 | 状态漂移 |
| 交叉引用 | 「来源」列引用卡牌编号/武将名在 cards.json/heroes.json 中存在；缺失/改名 → 报警 | 引用失效 |
| 已确认区块指纹 | 对 `[已确认(日期,依据)]` 区块记录哈希，非修订操作改变 → 拒绝 | LLM 回归改写 |
| 章节结构指纹 | 0~7 章标题与顺序不可变（hash 比对） | 结构破坏 |
| 数据段一致性 | 0.1/0.2/3.1/3.2/3.5/5.2 数据快照与 data/*.json 比对：全自动差异 WARN、候选/校验点 INFO（sync_rule_stats） | 数据段过时 |

> 落地状态：P0 三件套（解析回声/块 ID 唯一/章节结构）与 P1（ID 稳定性、FAQ 编号、确认状态一致性、交叉引用、块指纹）均已实现；
> 快照文件已落地 `scripts/.rule_doc_snapshot.json`（与 .rag_state.json 同风格）；`--strict` 可进 CI/pre-commit，`maintain_rag.py --strict-audit` 时失败即中止。

## 7. 维护节奏（与现有周更合并）

| 场景 | 触发 | 动作 | 耗时 |
|---|---|---|---|
| 热修/数值微调 | 官方小更新 | diff → 判定"不动 T0" → 只重跑数据语料 | 已有手册 |
| 常规周更 | 官方周更新 | 分流 → 若涉新机制：提案-确认 → 合入 → 校验 → 重建 → 回归 | 额外 30~60 分钟 |
| 大版本/新赛季 | 大量新武将/新机制 | 同上，提案量 10~30 条，逐条确认；**绝不整篇重整合** | 半天~1 天 |
| 疑难消化 | 实战/测试遇到答不出的组合 | 登记疑难 → 周会消化为 FAQ 提案 | 每周固定时段 |

回归测试要点（周更手册步骤 7 的 T0 专项）：
- **裁定回归集**：把 FAQ 79 条转成问句形成固定评估集（版本化存档），每次 T0 变更后全跑；
- 断言：已确认裁定答案**文本语义不变**（防 LLM 改写），新增裁定答对；
- 新机制题目加入评估集，形成滚动回归集。

## 8. 盲点闭环：FAQ 增补协议

FAQ 是 T0 文档里增量价值最高的部分（组合结算裁定），维护协议：

1. **疑难登记**：应用/测试中任何"答不出或答错"的组合结算 → 记入 `docs/元规则整理-完整版.md` 第 7 章
   （改造为"进行中清单"：未确认项 + 疑难登记），格式：`[疑难] 问题描述 | 涉及技能/卡牌 | 登记日期`；
2. **定期消化**：每周固定时段，把疑难逐条转成 FAQ 提案（LLM 起草 → 人确认 → 合入 5.x 末尾）；
3. **公告反向核对**：官方公告中的"修正/澄清"条目直接生成 FAQ 提案（官方裁定优先级最高，标注来源=公告）；
4. 第 7 章改造建议：现状全部是划掉的已确认项（历史价值），建议**把已确认项移到 changelog 附录**，
   第 7 章只保留进行中项——让"未决事项"一眼可见（也可考虑在知识库维护 UI 加"待确认清单"页签）。

## 10. 速查：变更 → T0 动作

| 情形 | 动作 | 位置 | 编号 |
|---|---|---|---|
| 新机制（时机/状态/术语/资源/区域/牌型） | 提案新增，标 [待确认] → 确认 | 对应章节末尾新 `###` 小节 | 章节内节序号 |

## 附：为什么不做"整篇重整合"

- 已确认表述会被 LLM 概率性改写 → 裁定语义漂移，回归测试难兜底；
- 79 条 FAQ + 37 章节块逐条重确认成本随文档增长线性上升，每周不可持续；
- 块 ID 全部变化 → 索引全量重建 + 审计/引用历史断裂。
增量协议下，每周实际人工投入 = 只审变更项（5~20 条），与"数据语料只审变更项"的原则同构。
