# 周更操作手册（语料更新）

> 适用范围：每周官方对武将/卡牌进行强度调整（加强/削弱/新增/下架）后，
> 按本手册更新规则专家语料。
> 核心原则：**数据源驱动 → 脚本重跑 → 只审变更项**，不手改语料文件。

---

## 1. 更新总览

| 层 | 内容 | 更新方式 |
|---|---|---|
| 数据源驱动 | 武将/卡牌/加强削弱/点数花色/装备属性语料 | 脚本全量重跑（自动） |
| 半自动 | 索引字段（时机/触发条件/关键词/关联） | 重跑 + LLM 只精化变更项 |
| 人工确认 | 元规则/FAQ/装备属性表/待确认清单 | 仅当变更引入新机制时 |

---

## 2. 前置：建立基线快照（首次必做）

更新前必须有"上次的版本"才能对比出差异。

1. 保存当前 3 份源数据副本（或依赖 git 版本管理）：
   - `data/heroes.json`、`data/cards.json`、`data/card_annotations.json`
2. 记录语料版本指纹（各语料 json 的生成时间/哈希）
3. 版本标记：武将/卡牌语料使用源数据 `last_updated` 字段作为版本号

---

## 3. 周更流程（7 步）

### 步骤 1：获取新数据
- 从官方渠道获取更新后的 `heroes.json` / `cards.json` / `card_annotations.json`
- **覆盖前先备份旧文件**（复制到 `backup/2026-08-14/` 或依赖 git）
- 若新增卡牌：同步补充 `mjs卡牌点数.xlsx`（花色点数）与装备属性表（攻击范围/距离修正）

### 步骤 2：差异检测（diff）
运行差异脚本，对比基线，输出**变更清单**：

| 变更类型 | 判定方式 | 处理 |
|---|---|---|
| 新增武将/卡牌 | 新出现的 id | 生成语料 + 精化 + 若新机制则更新元规则 |
| 技能/数值调整 | `last_updated` 变化或内容 diff（description/settlement/max_hp/max_hand/加强削弱效果） | 重跑 + 精化 + 人工核对公告 |
| 下架/删除 | 消失的 id | 标记下架（建议保留历史，勿直接删语料） |

> 变更清单建议字段：`类型 | id | 名称 | 变更摘要 | 是否涉及新机制`

### 步骤 3：全量重跑生成脚本

> **推荐入口**：改完 T0 文档后直接运行 `python scripts/maintain_rag.py`（增量）或 `--force`（全量），
> 会自动按依赖顺序调用下列脚本并校验块数；`--check` 可先预览变更。
> 语料重建成功后，建议加 `--build-index` 同步重建向量索引（或稍后运行 `python -m rag.cli --rebuild-index`；
> 不带 `--build-index` 时脚本结束也会给出提示）。
> 如需单独重跑某个语料，仍可依次运行（现有脚本位于 `scripts/`）：
```
build_rag_corpus.py    武将语料（171总览 + 418技能块）
build_card_corpus.py   卡牌语料（49块 + 装备属性注入）
build_modify_corpus.py 加强削弱语料（49块）
build_cardpts.py       点数花色语料（49块）
build_equip_attr.py    装备属性语料（27块）
build_rule_corpus.py   元规则切块/术语/FAQ（如元规则文档有更新）
build_special_corpus.py 特殊机制语料（专属牌/专属战法牌/特殊牌区/状态/概念）
```
检查生成日志：块数、抽取覆盖率是否正常；**留意 `TRIGGER_OVERRIDES 失效条目` 警告**（技能改名/删除时出现，需同步更新 `build_rag_corpus.py` 中的人工精化映射表）。

> **防覆盖**：重跑前确认脚本跳过 `curated`（人工/LLM 已精化）字段，只覆盖数据源字段。

### 步骤 4：LLM 精化变更项（可选，需 API）
- 打开应用「知识库维护」→「索引精化」，对待精化块（无 curated 且索引字段为空）执行「LLM 建议（当前/全部）」，人工确认后「保存当前/保存全部」
- 精化结果写入块的 `curated` 字段（method=llm/manual），重跑 build 脚本不覆盖
- 已精化条目不会重复出现在待精化清单中

### 步骤 5：人工审阅变更（最重要）
- **数值/描述调整**：对照官方公告逐条核对语料文本
- **新机制**（新时机/新牌型/新术语/新资源）：更新《元规则整理-完整版》+ 待确认清单
- **新增装备**：补装备属性表（细分/攻击范围/距离修正），新增坐骑补距离±1
- **新增卡牌**：补点数花色表；若涉及判定（如新卜卦牌），确认判定符号原文
- **加强/削弱**：若官方给出额外结算详情，填入 `settlement_detail` 字段

### 步骤 6：更新 changelog（变更日志）
记录：`日期 | 变更对象 | 变更内容 | 影响规则`
changelog 本身是高价值语料（玩家问"本周谁被削了"直接命中）。

### 步骤 7：回归验证
- 跑测试集（50~100 题真实结算问答）
- 重点看**变更武将/卡牌相关题目**的准确率变化
- 若从对变错 → 反推问题语料块/规则，修正后重测

## 4. 防踩坑清单

| 坑 | 解法 |
|---|---|
| 全量重跑覆盖人工精化字段 | 语料分 `source`（可覆盖）/ `curated`（保留）两档，重跑脚本跳过 curated |
| 更新前没备份 | 固定备份目录 + 依赖 git |
| 旧版本规则污染新答案 | 每个块带 `version`，回答时声明依据版本 |
| 新机制漏进元规则 | diff 时显式标记"是否涉及新机制"，触发人工审阅 |
| 删除武将直接删语料 | 标记下架/停用，保留历史（攻略可能引用旧版本） |
| 胜率等统计数据混入规则语料 | 单独一类"参考数据"语料，带版本/口径，不当规则用 |
| 人工精化映射表（TRIGGER_OVERRIDES）未同步 | 官方更新 heroes.json 后：技能改名/删除会触发脚本警告；同名技能描述变更需人工对照新描述重新审核该条触发条件并更新映射表 |

---

## 5. 每周更新检查清单（Checklist）

- [ ] 备份旧数据（backup/日期 或 git commit）
- [ ] 放入新数据（3 份 JSON；新增卡牌则补 xlsx/装备表）
- [ ] diff 输出变更清单，人工确认无遗漏
- [ ] 全量重跑生成脚本，无报错
- [ ] 检查 TRIGGER_OVERRIDES 失效警告并同步映射表（技能改名/删除/描述变更）
- [ ] 确认 curated 字段未被覆盖
- [ ] 变更项 LLM 精化完成
- [ ] 新机制已更新元规则 + 待确认清单
- [ ] changelog 已更新
- [ ] 测试集回归通过（变更项准确率无回退）

---

## 6. 耗时预估（供排期参考）

| 步骤 | 耗时（每周） |
|---|---|
| 获取数据 + diff | 10~20 分钟 |
| 重跑脚本 | 5 分钟 |
| LLM 精化（变更项） | 10~30 分钟 |
| 人工审阅（变更项） | 30~60 分钟 |
| changelog + 回归测试 | 20~30 分钟 |
| **合计** | 约 1.5~2 小时/周 |

## 7. 附：变更类型 → 处理动作速查表

| 变更 | 重跑 | 精化 | 人工核对 | 元规则 | 备注 |
|---|---|---|---|---|---|
| 数值微调（体力/手牌上限） | ✅ | ✅ | ✅ | 通常否 | 核对公告数值 |
| 技能描述改写 | ✅ | ✅ | ✅ | 可能（若时机变化） | 对比 diff |
| 新增武将（复用已有机制） | ✅ | ✅ | ✅ | 否 | 补全语料即可 |
| 新增武将（新机制） | ✅ | ✅ | ✅ | ✅ | 走待确认流程 |
| 加强/削弱效果调整 | ✅ | ✅ | ✅ | 可能 | 补结算详情 |
| 新增卡牌 | ✅ | ✅ | ✅ | 可能 | 补点数花色/装备表 |
| 新牌型/新资源/新区域 | ✅ | — | ✅ | ✅ | 高优先级人工 |
| 武将下架 | — | — | ✅ | 否 | 标记停用，保留历史 |

## 8. 可视化维护入口（2026-08 新增）

- 武将分类：应用内「知识库维护 → 武将分类维护」页签，维护分类/克制链/武将归类，保存后自动写回 data/hero_classification.json 并刷新语料状态；未归类武将可一键定位补充。
- 专属牌：应用内「知识库维护 → 专属牌维护」页签（原资料库入口已迁移）。
- 维护后仍需在「语料状态」页执行「重建武将语料」或「重建全部语料」。
