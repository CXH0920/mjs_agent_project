## 二、严厉结论

这个项目最危险的不是单个算法写错，而是多次在**证据不足时宣布修好**：红灯测试被称为“预置问题”，错误 Python 环境导致 UI 测试被跳过，OCR 单样本通过被扩大成普适结论，回退被当作解决，异步化被当作线程安全，修正写入逻辑被当作已恢复丢失数据。旧版复盘本身也把多项“部分解决”写成了肯定句。

冻结点仍需优先处理的风险如下：

1. 历史中暴露过真实 API Key，且助手原样复述；现有记录没有证明已经轮换或吊销。
2. GUI 线程仍可能执行 ADB、OCR 和模板制作；PaddleOCR 单例又可能跨线程共享，存在卡死、线程亲和和重建竞态。
3. 官网头像下载缺少域名、重定向、MIME、响应大小、解码和安全文件名校验。
4. JSON 只有单文件原子替换，没有文件锁、备份和跨文件事务；多进程写入仍可能丢数据。
5. QProcess 的半行缓冲与阻塞等待问题、UI 测试接口漂移、模态弹窗阻塞和资源路径回归仍未彻底消除。
6. OCR 完整人工真值样本远少于截图数量，不能声称“全图库准确率已验证”。
7. 依赖没有锁定，模型名与计价配置曾多次漂移，文档中的测试数和部分能力描述也曾失真。

## 三、逐项负面事件

下列事件按因果与维护领域归类，不按严重度掩盖小问题。每项的“解决”只描述证据显示实际做过的事，不替历史结论背书。

### A. 需求、规格与交付沟通

#### 1. PDF 需求材料无法读取，任务被迫中止

- **发生了什么**：最初收到 PDF 需求后，连续尝试 PyMuPDF、Conda 和不同路径均失败，最终用户中止该会话，改用 TXT 重新开始。
- **怎么发现的**：工具连续报告依赖缺失、环境不可写、路径不存在或网络受限，没有成功提取正文。
- **怎么解决的**：没有修复 PDF 链路，只是由用户提供 TXT 绕过。
- **根本原因**：开始前没有盘点本机已有解析工具和准确解释器，随后用猜测路径与临时装依赖扩大了失败面。
- **以后怎么预防**：先检查系统工具和项目环境；缺依赖时立即说明边界并请求可读文本，不连续试错。
- **状态与证据**：**部分解决（绕过）**，A；2026-06-06 Codex 会话 `019e9b8b...`。

#### 2. 初始需求边界严重不完整

- **发生了什么**：平台、输入来源、实时性、推荐链路、数据来源、MVP 和非目标都没有被需求文档锁定。
- **怎么发现的**：实现前必须连续追问，才确认手机游戏、PC 模拟器、OCR、只做选将与资讯、AI 内容预生成等关键约束。
- **怎么解决的**：通过对话补齐范围后分阶段实施。
- **根本原因**：需求材料偏概念描述，缺少可执行的系统边界和验收条件。
- **以后怎么预防**：立项模板强制包含“平台、输入、延迟、数据源、输出、非目标、MVP、验收样本”。
- **状态与证据**：**已解决（需求澄清）**，A；2026-06-06 Codex 会话 `019e9b93...`。

#### 3. “阶段完成”被误解为完整产品可运行

- **发生了什么**：阶段二结束后，用户仍需追问当前产物是否只是框架；实际只有数据层和爬虫可用，AI 依赖 Key 与 Prompt，后续阶段尚未实现。
- **怎么发现的**：用户依据“阶段完成”的表述形成了比实际更高的完成度预期。
- **怎么解决的**：后续重新解释已完成、需配置、骨架和未实现部分。
- **根本原因**：进度汇报只按计划阶段表述，没有同时列运行前提和缺失能力。
- **以后怎么预防**：每次交付使用“可直接运行、需外部配置、只有骨架、未实现”能力矩阵，并给出最短验证命令。
- **状态与证据**：**已解决（沟通纠偏）**，A；2026-06-06 Codex 会话 `019e9b93...`。

#### 4. Prompt 未经确认就写入文件

- **发生了什么**：用户要求先展示草案、认可后再落盘，但相性 Prompt 已经直接写入；用户不满意后要求参考其六维 Prompt 重做。
- **怎么发现的**：用户明确指出内容不满意，并重申确认闸门。
- **怎么解决的**：重新按用户样例设计，经反馈后再更新。
- **根本原因**：把“先确认”当成建议，而不是验收前置条件。
- **以后怎么预防**：涉及 Prompt、视觉稿和不可逆数据迁移时，在任务清单中设置显式确认闸门；未确认只输出草案。
- **状态与证据**：**已解决，但发生一次无效落盘**，A；2026-06-06 Codex 会话 `019e9bf5...`。

#### 5. Prompt 修改了错误文件，且没有备份

- **发生了什么**：应修改 `synergy_score.md` 的任务被错改为 `hero_guide_prompt.md`；会话记录显示没有备份，错误改动也没有被确认还原。
- **怎么发现的**：用户指出真正目标文件与已修改文件不一致。
- **怎么解决的**：随后转向正确的相性 Prompt，但原错误文件的恢复证据缺失。
- **根本原因**：多个临时目录中存在近似命名 Prompt，执行前没有核对真实路径和 Git 差异。
- **以后怎么预防**：修改前用 `rg --files` 和标题内容双重确认目标；修改后只检查目标文件 diff；未提交文件先做可恢复快照。

#### 6. Prompt 规格连续暴露内部矛盾

- **发生了什么**：Prompt 先后出现“六维/七维”数量不一致、JSON 缺新增字段、规则与卡牌依赖冲突、缺少特殊游戏规则、遗漏 `cards.json` 等问题；补资料后再次返工。
- **怎么发现的**：逐轮审查 Prompt 与示例 JSON、卡牌数据和游戏规则时发现字段及约束对不上。
- **怎么解决的**：补充卡牌上下文、字段和特殊规则，并把静态“被某武将克制”改为更耐平衡更新的“被某类能力克制”。
- **根本原因**：Prompt、Schema、业务规则和数据文件没有单一事实源，也没有契约测试。
- **以后怎么预防**：由 Schema 生成字段清单；用固定样例验证维度数、必填键和规则覆盖；Prompt 只在一个受版本控制的位置维护。
- **状态与证据**：**已按当时需求修订，版本漂移风险仍在**，A/B；Codex 临时目录相关会话。

#### 7. 擅自加入计划外 `SkillType`

- **发生了什么**：实现者主观增加了计划中不存在的技能类型，并扩散到模型、爬虫、输出和测试。
- **怎么发现的**：用户对照计划发现字段不在约定范围内。
- **怎么解决的**：删除枚举、字段、输出和相关测试。
- **根本原因**：把个人领域推断当成已批准的 Schema 需求。
- **以后怎么预防**：数据模型新增字段必须附需求来源、迁移影响和示例；无依据不扩展。
- **状态与证据**：**已解决**，A；2026-06-07 Codex 会话 `019e9c63...`。

#### 8. 数据模型在编码后才被真实样本推翻

- **发生了什么**：早期 `title/difficulty/mode_viability` 等字段不符合真实数据，之后又补体力、手牌、性别、技能嵌套和卡牌模型；计划文档还出现重复章节。
- **怎么发现的**：接入真实官网样本后，现有模型无法表达实际结构。
- **怎么解决的**：调整模型、补充卡牌实体并修正文档重复段落。
- **根本原因**：在编码前没有用一批真实样本冻结 Schema。
- **以后怎么预防**：先保存代表性原始样本，完成字段盘点和 Schema fixture，再写模型和迁移。
- **状态与证据**：**已解决当时差异**，A；2026-06-06 Codex 会话 `019e9bf5...`。

#### 9. 推荐指数目标超出数据能力，公式又把排名误当概率

- **发生了什么**：初版把榜单排名当概率，`1-B` 除法把最高项放大约 20 倍；还存在 `P=0` 一票否决、`P5=P95` 除零、排名等距、无样本量等假设，无法支持“当前对局最优英雄”的强结论。
- **怎么发现的**：对公式做边界值和含义审查后，发现数值尺度与数据语义不成立。
- **怎么解决的**：产品定位降级为“全服静态热门强势参考指数”，修订公式的一部分；部分数据限制由用户明确接受。
- **根本原因**：先定产品结论，再反推有限的静态榜单数据；缺少统计定义、边界测试和不确定性表达。
- **以后怎么预防**：先写指标的数据字典与可解释范围；对零值、常数分位数、极端排名和缺样本做测试；UI 明示“参考指数”而非概率。
- **状态与证据**：**已接受风险/部分解决**，A；Codex 临时目录需求会话。

#### 10. 官方榜单和 OCR 页面边界曾被错误泛化

- **发生了什么**：榜单解析一度倾向写死 160 行；同时有人试图把官方整榜的唯一补全策略直接复用到四槽、八槽页面。
- **怎么发现的**：讨论榜单增长、横线长度变化和不同页面候选空间时发现假设不成立。
- **怎么解决的**：榜单改为动态检测横线与实际角色数；OCR 方案明确白名单是安全边界，整榜唯一性不能替代局部页面证据。
- **根本原因**：把当前数据规模和一个页面的全局约束误当成永久、通用规则。
- **以后怎么预防**：解析数量从页面结构推导；每个 OCR 场景单独定义候选集、唯一性和降级策略。
- **状态与证据**：**设计层已纠偏**，A；Codex 临时目录相关会话。

#### 11. 文档同步长期依赖用户追问

- **发生了什么**：README、PLANS、字段说明和调用图在代码变更后多次没有同步，至少十余次由用户额外提醒；还有一次阶段一表格替换没有真正保存。
- **怎么发现的**：用户对照实现与文档发现描述滞后或缺失。
- **怎么解决的**：每次被指出后补文档；后来把文档同步写入项目规则。
- **根本原因**：完成定义只覆盖代码和局部测试，不包含文档一致性检查。
- **以后怎么预防**：每个任务的 DoD 固定列出受影响的 README、规格、调用图、运行手册和数据说明；结束前用关键词交叉检索。
- **状态与证据**：**流程规则已补，历史上反复发生**，A；多次 Codex 会话。

### B. 工具链、编码、测试与 Git

#### 12. 工具执行长期失控，约 223 次非零输出

- **发生了什么**：早期主会话累计出现约 223 次非零工具输出，集中在 PowerShell 引号与 Here-string、错误路径、GBK/Unicode、BOM、超时、错误 Python 环境和缺失插件。
- **怎么发现的**：对历史工具结果去重统计后发现，这不是偶发失败，而是贯穿多个阶段的工作方式问题。
- **怎么解决的**：逐次修正命令，后来项目规则固定绝对 Python 解释器、最小补丁和定向测试。
- **根本原因**：大量依赖脆弱的内联脚本和单次 `conda activate`，没有先验证命令前提，也没有在同类失败后改变策略。
- **以后怎么预防**：首选短命令、`rg`、`apply_patch` 和项目绝对解释器；同类失败两次即停下来修正方法，不继续堆转义。
- **状态与证据**：**流程已改善，历史损耗不可逆**，A；2026-06 至 07 多个 Codex 会话。

#### 13. UTF-8、BOM、控制台编码和换行反复出错

- **发生了什么**：JSON 带 BOM、中文控制台输出失败、测试文件缩进损坏、PowerShell 写入引入 BOM，以及 LF/CRLF 警告先后出现。
- **怎么发现的**：解析报错、Python 编译失败、乱码、Git 换行警告和测试收集失败暴露问题。
- **怎么解决的**：逐个文件修复编码或缩进，并最终明确 UTF-8、LF、无 BOM、无控制字符的仓库规范。
- **根本原因**：混用 PowerShell 默认写入语义、不同终端编码和不稳定的批量文本替换。
- **以后怎么预防**：编辑统一经补丁工具；CI 校验 BOM、CRLF 和控制字符；日志输出显式 UTF-8；禁止用管道整文件回写源码。
- **状态与证据**：**已建立规范，历史上多次复发**，A；早期 Codex 会话及贾诩修复提交旁证。

#### 14. 手写 JavaScript 解析器造成死循环和尾逗号返工

- **发生了什么**：为解析官网 JS，手写字符扫描器把 `continue` 放错位置导致死循环和多次超时；修完后又被尾逗号击穿。
- **怎么发现的**：定向测试挂起，修正循环后新的真实样本继续解析失败。
- **怎么解决的**：修正游标推进并补尾逗号清理，相关测试最终 39 项通过。
- **根本原因**：用临时字符串逻辑承担完整 JS 子集解析，却只覆盖理想样本。
- **以后怎么预防**：优先结构化解析库；必须自建适配器时，先收集 `undefined`、裸 key、单引号、尾逗号、嵌套和转义的契约夹具，并给解析加超时。
- **状态与证据**：**已解决当时样本，解析方案仍偏脆弱**，A；2026-06-06 Codex 会话 `019e9b93...`。

#### 15. PowerShell 大块重写破坏源码

- **发生了什么**：批量替换曾损坏中文、删除 `_update_skills` 等方法、破坏 import、引入 BOM、字符串未闭合和语法错误。
- **怎么发现的**：编译、导入、运行和成员查找连续失败；部分问题由用户直接指出界面功能消失。
- **怎么解决的**：从上下文或 Git 恢复缺失代码，逐个修复语法、导入和编码。
- **根本原因**：为图快使用整段脚本重写，而不是局部补丁；写完也没有立即编译与核对成员清单。
- **以后怎么预防**：禁止脚本整文件替换业务源码；每个小补丁后立即 `py_compile`、导入并运行受影响测试；改 UI 时同时核对关键方法和信号。
- **状态与证据**：**具体破坏已恢复，方法风险已由规则约束**，A；2026-06-10 Codex 会话 `019eb005...` 等。

#### 16. 爬虫解耦在方案确认前开工，并漏改调用方

### C. 数据、爬虫与持久化

#### 26. 增量爬虫把 `heroes.json` 覆盖到只剩诸葛亮一条

- **发生了什么**：指定武将模式把 `merged = validated` 当成完整结果写回，真实 `heroes.json` 一度只剩诸葛亮 1 条。
- **怎么发现的**：运行后检查数据文件条数，发现其他武将全部消失。

- **以后怎么预防**：使用显式模式枚举；写入流程固定为“输入快照→staging→完整校验→原子替换→失败保留旧数据”；验证总数和未选记录不变。
- **状态与证据**：**写入逻辑已修，历史数据恢复证据不足**，A；2026-06-07 Codex 会话 `019e9c63...`。

#### 60. 日志系统同时存在七类缺陷

### F. OCR、截图与官方数据导入

#### 61. 固定 ROI 不适配分辨率，高置信度又掩盖截断

- **发生了什么**：早期固定坐标在不同分辨率下失效，替换模板还残留旧参考尺寸；后来“祝融夫人”被截成“祝融夫”，却因 OCR 置信度高而提前返回。
- **怎么发现的**：不同尺寸真实截图和名称结果对比显示裁剪范围不完整，而非单纯识别模型差。
- **怎么解决的**：增加参考分辨率缩放、多尺度模板匹配、替换时清理旧元数据；名称 ROI 高度从 140 调到 145，并加诊断日志。
- **根本原因**：把固定像素和高置信度当作跨分辨率、跨长度的可靠条件。
- **以后怎么预防**：ROI 与页面类型、参考分辨率一一绑定；先做字数完整性门禁，再看置信度；保留长姓名和边缘裁剪样本。
- **状态与证据**：**部分解决；“祝融夫人”真实根因仅推测为 ROI/截断，高置信短路当时未根治**，A/B；Codex early #27、Claude C13。

#### 62. P1 “王翦→王异”先基于错误事实打了补丁

- **发生了什么**：最初认为 PaddleOCR 直接把“王翦”读成“王异”，于是增加低置信邻近候选回退；后续原始调试才证明 OCR 实际输出是“王剪”，“王异”是旧纠错算法自己造出来的。
- **怎么发现的**：保存并打印 OCR 原始输出后，真实输入与先前推断不一致。
- **怎么解决的**：先修相同字符评分、增加低置信回退；后来在 P3 中删除这个破坏性临时路径。
- **根本原因**：没有区分“模型原始输出”和“纠错后输出”，在根因证据不足时直接编码。
- **以后怎么预防**：诊断必须记录原图、裁剪图、每路 OCR 原文、置信度、候选和最终决策；临时补丁要标删除条件。
- **状态与证据**：**初始方案已被后续替代**，A；`project_problem.md` P1/P3。

#### 63. P2 用 Unicode 码位差模拟字形，正确结果只是巧合

- **发生了什么**：`王剪` 在“王异/王翦”之间平分，旧算法按遍历顺序选错；`王翡→王翦` 能成功，仅因为两字 Unicode 码位相近，并非视觉算法正确。
- **怎么发现的**：计算“剪/翦/异/翡”的码位差并回放截图，发现码位与字形没有稳定关系。
- **怎么解决的**：改用四角号码、仓颉码和部首的加权特征，9 张当时截图通过。
- **根本原因**：把 Unicode 编码分配误当成视觉空间。
- **以后怎么预防**：相似度必须来自可解释字形特征或图像证据；任何“恰好通过”的样本都要做反例检验。
- **状态与证据**：**Unicode 方案已删除；后续又发现新特征缺值问题**，A；`project_problem.md` P2。

#### 64. P3 的低置信回退把正确名字改成别的合法名字

- **发生了什么**：P1 临时逻辑在置信度低于 0.97 时直接取第一个邻近候选，导致“蒙毅→乐毅”“吕雉→吕蒙”。

- **根本原因**：临时补丁基于错误假设，且修复根因后没有主动清理。
- **以后怎么预防**：每个补丁记录服务的具体失败样本；根因修复合入时审计所有临时分支；合法完整名称不能仅因低置信被任意替换。
- **状态与证据**：**已解决该回归**，A；`project_problem.md` P3。

#### 65. 高置信保护先后绕过“赢政”和“贾诩”纠错

- **发生了什么**：错误“赢政”以 0.9953 被高置信保护；另一次“贾诩”被识别为“贾谢”时，高置信分支直接保留 OCR 原文，跳过统一词表纠正。

- **根本原因**：把置信度当正确性证明，且相同规则在多个入口次序不一致。
- **以后怎么预防**：统一名称决策服务；完整合法候选、未知新名和疑似错字分别建策略；高置信只是一条证据，不能越过安全白名单。
- **状态与证据**：**已解决已知路径；旧 CSV 仍需重新导入并重建指数**，A/B；Codex 旧报告 #41、丢失会话旁证。

#### 66. 旧“多候选字形评分”仍在代码里，生产主链却绕过

- **发生了什么**：commit `bbc0ede` 后，代码和文档仍描述多候选字形决胜，但生产主链并未调用它，`王翡` 只得到 `[王异, 王翦]` 并保持 unresolved。

#### 67. 新候选闭包方案又暴露三个安全缺陷

- **发生了什么**：严格前缀优先会吞掉合法等长候选，如 `赵婕→赵婕妤` 时忽略 `赵姬`；`uncertain` 的增删字结果仍可被页面唯一性强行确认；缺失四角码被填成 `00000`，两边都缺失反而贡献 0.4 假相似。
- **怎么发现的**：独立审查先写失败用例，三个用例分别证明候选丢失、错误强确认和缺值伪证据。
- **怎么解决的**：保留完整候选闭包；禁止 uncertain 增删字被页面唯一性升级；缺失特征不计分。OCR/业务 93、推荐 UI 30、对局 UI 9 项通过。
- **根本原因**：优化时把“更精确”与“更安全”混同，缺失值又被当作真实编码参与相似度。
- **以后怎么预防**：候选过滤只允许减少已证明不可能项；状态升级必须要求新增证据；缺失特征保持 `None`，绝不填有语义的零码。
- **状态与证据**：**已解决三项审查问题**，A；2026-08-01 前 Codex 会话。

#### 68. OCR 截图很多，但完整人工真值远远不够

#### 71. 单字高置信让樊哙、郭隗、荆轲、范雎缺字

- **根本原因**：把字符置信度等同于字符串完整性，没有字数门禁。
- **以后怎么预防**：先按页面与候选定义允许长度；缺字只能用白名单证据补全，不能靠最高分硬选。

#### 72. “荀勖”受 OCR 模型字表硬限制

- **发生了什么**：简体模型不含或不能稳定输出“勖”，三处样本只识别为“荀”。
- **怎么发现的**：多个样本一致缺字，并检查模型字符集合确认能力边界。
- **怎么解决的**：用繁体模型在候选白名单内兜底；仍不唯一就待复核。
- **根本原因**：模型类别集合有限，这不是调一个阈值能修复的问题。
- **以后怎么预防**：上线前盘点词表字符覆盖；罕见字使用受限候选或专用模型；不得手改模型字典假装已支持。
- **状态与证据**：**安全降级已实现，主模型能力未解决**，B；Codex 旧报告 #31。

#### 73. 短虚线漏检导致两行榜单粘在一起

- **发生了什么**：新版表格的短水平虚线没有被旧 Hough 参数识别，一个 ROI 中包含视觉上的两行。
- **怎么发现的**：保存行切片后直接看到两行粘连。
- **怎么解决的**：聚合短水平线，并根据稳定行距补推边界。
- **根本原因**：分行算法只适配旧版长实线。
- **以后怎么预防**：保留行切片快照和行高分布；表格版式更新时同时回放旧、新样本。
- **状态与证据**：**已解决当时版式**，B；Codex 旧报告 #32。

#### 74. 官方导入长时间无进度，2v2 双表还混在一起

- **发生了什么**：长任务没有可见进度；2v2 左右两张榜单没有独立解析和落盘，用户无法判断卡住还是工作中。

#### 75. 不同页面错误共用 ROI 和参考分辨率

#### 76. “夏侯惇”公共前缀会随词表扩充静默误绑

#### 77. OCR 冷启动和模板匹配过慢

- **发生了什么**：模板匹配约 550 ms，模型冷启动约 4.5 s；用户第一次操作明显卡顿。
- **怎么发现的**：分阶段计时日志定位到全屏多尺度模板和 PaddleOCR 初始化。

- **以后怎么预防**：先 profile 再优化；预热显示明确状态；快路径与慢路径必须做结果一致性回归。
- **状态与证据**：**性能已改善；线程安全风险另见持续风险**，B；Codex 旧报告 #46。

#### 78. 拼图快路径把单字“王”扩成“王异”

- **发生了什么**：批量拼图裁剪只留下“王”，编辑距离流程却把信息不足的单字扩成完整“王异”；逐槽慢路径原本能得到“王翦”。

- **以后怎么预防**：任何批处理优化都要与基线逐样本对比；信息量下降时不能升级为自动确认。

#### 79. 官网新版分页和短虚线让旧解析整体失效
