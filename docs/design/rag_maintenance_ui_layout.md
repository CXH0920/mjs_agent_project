# 知识库维护板块 UI 布局与职责分类设计

> 适用范围：主导航第 4 页「知识库维护」（`src/ui/maintenance/rag_maintenance_panel.py`）及其全部页签/对话框：
> `src/ui/maintenance/rule_doc_panel.py`、`src/ui/maintenance/card_points_panel.py`、`src/ui/maintenance/equip_attrs_panel.py`、
> `src/ui/library/special_cards_panel.py`、`src/ui/library/hero_classification_panel.py`、`src/ui/maintenance/index_refinement_dialog.py`。
> 状态：第一步（纯布局改造：元规则子页签化 + 语料状态页调整 + 页签顺序）已实施；审计联动为后续步骤。

## 背景与现状

知识库维护是 RAG 语料/索引的本地维护工作台，现状为 6 页签平铺 + 1 个模态对话框：

| # | 页签 | 实现文件 | 数据源 | 维护方式 |
|---|------|---------|--------|---------|
| 1 | 语料状态 | `rag_maintenance_panel.py` 内建 | 无（只读监控 8 个语料任务） | 按钮触发 `maintain_rag.py` |
| 2 | 专属牌维护 | `library/special_cards_panel.py` | `data/special_cards.json` | 对话框编辑，改即写 |
| 3 | 卡牌点数维护 | `maintenance/card_points_panel.py` | `data/card_points.json` | 对话框编辑 + xlsx 应急导入 |
| 4 | 装备属性维护 | `maintenance/equip_attrs_panel.py` | `data/equip_attrs.json` | 表格直编 + 手动保存 |
| 5 | 武将分类维护 | `library/hero_classification_panel.py` | `data/hero_classification.json` | 3 个子页签 + 手动保存 |
| 6 | 元规则维护 | `maintenance/rule_doc_panel.py` | `docs/元规则整理-完整版.md` 等 | 4 卡片纵向堆叠 + 脚本执行 |
| — | 索引精化（对话框） | `maintenance/index_refinement_dialog.py` | `data/rag_corpus/*.json`（语料产物） | 左清单 + 右字段编辑 |

现状问题：

1. 元规则维护页 4 个能力卡片 + 底部日志 = 5 个纵向区块一次性堆叠，页签内容过长，且四个区块职责跨度大（监控 / 同步 / 提案 / 待办），用户一次只看一个；
2. 语料状态页操作栏 5 个按钮平铺（刷新/索引精化/重建武将/重建全部/重建语料+索引），主次与分组不分明；
3. 语料状态页纵向三段（表 → 审计 → 日志），日志区常驻占高，审计信息被夹在中间；
4. 元规则维护（T0 规则母本入口）排在最后一个页签，与其权威地位不符。

## 目标

1. 页面职责三层分离：**运维中枢**（语料状态）+ **文档规则域**（元规则）+ **数据源编辑域**（4 个 JSON 编辑页签），各归其位、互不干扰；
2. 每个编辑页签只对应一个权威数据源文件，语料/索引同步统一收敛到「语料状态」页，编辑页只负责标脏（发 `data_changed`）；
3. 单页内容超过 4 个区块必须拆页签或折叠，避免纵向滚动疲劳；
4. 任何保存动作都有统一反馈链：toast/状态条标脏 → 语料状态页「待重建」→ 重建后回绿。

## 页面级信息架构

```
知识库维护（主导航第 4 页）
│
├─ 一级页签（6 个，按"先监控全局 → 再维护权威源"排列）
│
│  A. 运维中枢 ── 语料状态（含索引精化入口，弹对话框）
│  B. 文档规则域 ── 元规则维护（T0 文档工作流）
│  C. 数据源编辑域 ── 专属牌 / 卡牌点数 / 装备属性 / 武将分类
```

页签顺序：**语料状态 → 元规则维护 → 专属牌维护 → 卡牌点数维护 → 装备属性维护 → 武将分类维护**。

元规则维护提到第 2 位：它是 T0 规则知识库母本的维护入口，重要度高于四个 JSON 编辑面板；「语料状态 + 元规则」构成"运维/规则"区，「四 JSON 编辑」构成"数据维护"区。

## 语料状态（运维中枢）

**职责**：全局状态监控（8 语料任务 × 待重建/最新/缺源）+ 人工审计清单 + 一键重建 + 执行日志 + 索引精化入口。

**布局**（左右分栏 + 底部折叠日志）：

```
┌──────────────────────────────────────────────────────────────┐
│ PageActionBar: [状态文字]  [刷新状态] [索引精化] │ [重建武将语料]│
│                [重建全部语料] [重建语料+索引]                  │
├──────────────────────────┬───────────────────────────────────┤
│ ① 任务状态表（左，8 行） │ ② 人工维护清单（右，审计）         │
│  语料任务|状态|块数|数据源 │  · 未归类武将 5 人        [去归类] │
│  武将语料 | ✓ | 123 | …   │  · 专属牌缺结算 3 个     [去补全] │
│  …8 行…                  │  无问题时显示绿色"检查通过"       │
├──────────────────────────┴───────────────────────────────────┤
│ ③ 执行日志（QSplitter 可拖拽/折叠，默认半高）                 │
└──────────────────────────────────────────────────────────────┘
```

要点：

- 操作栏按钮分两组，中间以竖线分隔：**查看类**（刷新状态 / 索引精化）与 **执行类**（重建武将语料 / 重建全部语料 / 重建语料+索引），「重建语料+索引」用 PRIMARY 强调；
- 日志区用垂直 QSplitter 承载，`setChildrenCollapsible(True)` 支持拖拽折叠，不常驻占高；
- 审计清单后续（第二步）改为可点击条目，支持跳转到对应编辑页签修复（去归类/去补全/去检查）。

## 元规则维护（文档规则域）

**职责**：T0 规则文档 `docs/元规则整理-完整版.md` 的全生命周期：机器校验（audit）、数据段同步（sync）、LLM 提案工作流（propose/apply）、疑难登记（pending → FAQ 提案）。

**布局**（4 个子页签 + 底部折叠日志）：

```
┌──────────────────────────────────────────────────────────────┐
│ PageActionBar: [状态文字]  [刷新状态(全量)]  [收起日志]        │
├──────────────────────────────────────────────────────────────┤
│ 子页签: [文档状态] [数据段差异] [提案工作台] [疑难登记]        │
│ ┌──────────────────────────────────────────────────────────┐ │
│ │ 文档状态: NoticeBanner(ERROR/WARN) + 3 行级别汇总表       │ │
│ │ 数据段差异: 差异表(段/行号/类型/摘要) + [应用已确认差异]   │ │
│ │ 提案工作台: 提案下拉 + [生成提案][合入] + 5 列明细表       │ │
│ │ 疑难登记: 4 列待办表 + [新增登记][转为FAQ提案]            │ │
│ └──────────────────────────────────────────────────────────┘ │
│ ③ 执行日志（QSplitter 可拖拽/折叠，所有脚本输出统一汇入）     │
└──────────────────────────────────────────────────────────────┘
```

要点：

- 4 个能力 → 4 个子页签，每个子页签内保持"标题行 + 操作按钮（右上）+ 表格"的卡片范式（复用 `ragTableSurface`）；
- 「刷新状态」触发串行 audit → sync（沿用 `_pending_sync` 机制）；
- 日志区与「语料状态」页共用同一外观（`ragLogSurface`），各自独立实例。

## 数据源编辑域（4 个 JSON 编辑页签）

| 页签 | 职责 | 布局 | 提交模式 |
|---|---|---|---|
| 专属牌维护 | 维护 `data/special_cards.json`（专属牌/专属战法牌/特殊牌区/状态标记/概念 5 类） | 顶栏（分类筛选+搜索+新增）→ 横向 QSplitter（左紧凑列表 / 右详情卡片+编辑删除） | 改即写 |
| 卡牌点数维护 | 维护 `data/card_points.json`（162 张牌面明细 + 12 条判定规则 + xlsx 应急导入） | 纵向 QSplitter（上牌面明细表 / 下判定规则表）→ 底部导入栏 | 改即写 |
| 装备属性维护 | 维护 `data/equip_attrs.json`（26 件装备，属性列可编辑） | 标题 → 5 列表格直编 → 底部提示+保存 | 手动保存 |
| 武将分类维护 | 维护 `data/hero_classification.json`（分类 CRUD/克制链/武将归类） | 顶部 ActionBar（脏标记+保存）→ 3 子页签，列表-详情 splitter | 手动保存（整单事务） |

现状布局已合理，本设计不做结构性改动；后续可选微调（卡牌点数表加名称过滤框、专属牌详情加"待重建提醒"小字）。

## 索引精化（对话框）

**职责**：对卡牌/武将语料中"无 curated 且索引字段为空"的块补全 timing / trigger_condition / keywords / related，支持 LLM 建议与人工填写。

**布局**（保持现状）：模态对话框，横向 splitter（左：待精化清单表 + LLM 建议/跳过；右：原文预览 + 4 字段编辑器）→ 底部（保存当前/保存全部/关闭）。

## 职责分类总矩阵

### 数据资产 → 归属 → 产物

| 权威数据源 | 维护面板 | 语料任务（8） | 读写 | 提交模式 |
|---|---|---|---|---|
| `data/heroes.json`、`data/cards.json` | 无面板（外部同步） | 武将/卡牌/加强削弱/装备（源之一） | 只读 | — |
| `data/special_cards.json` | 专属牌维护 | 特殊机制语料 | 读写 | 改即写（对话框保存） |
| `data/card_points.json` | 卡牌点数维护 | 点数花色语料 | 读写 + xlsx 覆盖 | 改即写 |
| `data/equip_attrs.json` | 装备属性维护 | 装备属性语料 | 读写 | 手动保存 |
| `data/hero_classification.json` | 武将分类维护 | 武将分类语料 | 读写 | 手动保存（整单事务） |
| `docs/元规则整理-完整版.md` | 元规则维护 | 元规则/术语/FAQ | 脚本化读写 | 脚本执行（audit/sync/提案） |
| `docs/rule_doc_pending.json` | 元规则维护·疑难登记 | —（待办） | 读写 | 改即写 |
| `data/rag_corpus/*.json`（产物） | 索引精化 | 卡牌/武将语料 | 写 curated | 改即写（重建保留） |

### 操作域划分

| 操作域 | 动作 | 归属板块 |
|---|---|---|
| 监控 | 任务状态计算、审计清单 | 语料状态 |
| 构建 | 重建语料 / 重建索引（QProcess 调 `maintain_rag.py`） | 语料状态 |
| 精化 | 索引字段补全（LLM/人工） | 索引精化对话框 |
| 数据编辑 | 4 个 JSON 的增删改 | 4 个编辑页签 |
| 文档规则 | audit / sync / 提案生成合入 / 疑难登记 | 元规则维护 |
| 应急导入 | xlsx → JSON 全量覆盖 | 卡牌点数维护 |

### 状态流（核心闭环）

```
[4 个编辑页签 改数据] ──data_changed──▶ [语料状态: 任务标"待重建" ⚠]
                                              │
                     [人工审计清单] ◀── 校验 ──┤
                                              ▼
                     [重建全部语料 / 重建语料+索引] ──▶ [任务转"最新" ✓]
                                              │
                     [索引精化(可选)] ◀── 待精化块提示 ──┘
```
