# 汉字相似度权重选型说明（四角 + 仓颉 + 五笔）

> 适用范围：`src/ocr/character_similarity.py` 的 `_multi_dim_similarity` 权重、`SAFE_CHARACTER_SIMILARITY` 阈值与 `SAFE_SUBSTITUTION_WHITELIST` 白名单。
> 生效时间：2026-08-05。

## 背景

原方案为「四角 40% + 仓颉 40% + 部首 20%」，实测存在两类缺陷：

- 四角号码只看四角笔形，对「同轮廓异部件」的形近字（嬴/赢、彧/或、侯/候、王/玉、荀/苟、姬/姫）完全同码（相似度 1.0），是 OCR 误纠的主要来源；
- 部首只区分"是否同部首"，对同部首形近字（侯/候、荀/苟、雎/雉、袁/表、宓/密）无区分力，仅剩"部首不同 = 0 分"的否决作用。

为提升形近字区分能力，将「部首」维度替换为「五笔 86 全码」（部件级编码，能区分部首/声旁不同的形近字），并重新选定三者权重。

## 目标

1. 绝大多数形近字可区分：词表内形近字对相似度低于安全阈值，不误绑；
2. 自动纠错量不降：OCR 错字→正字相似度达到安全阈值，减少人工确认；
3. 权重选择稳健：相邻权重不导致指标剧烈波动。

## 评测方法

### 层面一：端到端（名称级）

模拟 `correct_hero_name`：对 57 个「OCR 错名」（苟彧、庞暖、王剪、钟离昧…）在 169 个角色名候选内纠正，统计正确/误纠；另验证 7 个「错名同时命中多个角色名」的高风险场景（貂禅→貂蝉/刘禅、郭角→郭解/张角、李布→季布/李广…）。

结论：名称级评分中匹配字 +1.0 硬分主导，权重只影响 margin、不影响谁赢；所有候选权重均 100% 正确、0 误绑。

### 层面二：单字对（`is_safe_single_substitution` 路径）

- 应纠对 40 组：OCR 错字→正确词表字，期望相似度 ≥ 0.55（自动放行）；
- 不应混淆对 6 组：词表内形近字对（雎/雉、蝉/禅、解/角、青/清、季/李、超/赵），期望 < 0.55（不误绑）。

该层面无匹配字掩护，权重直接决定分数，故权重敏感。

| **0.3/0.3/0.4（选定）** | **23** | **1** |
| 0.2/0.4/0.4（保守） | 23 | 2 |
| 0.2/0.6/0.2（仓颉优先） | 26 | 2 |
| 0.4/0.3/0.3 | 22 | 3 |
| 0.3/0.2/0.5（仓颉偏低） | 24 | 3 |

选型要点：

- 四角权重 ≥ 0.4：四角同码盲区把不应混淆对推高，超标 3/6；
- 仓颉权重 ≤ 0.2：部件差异信号被稀释，超标 3/6；
- 0.3/0.3/0.4 落在稳健平台区，邻居权重（0.2/0.3/0.5、0.3/0.4/0.3、0.25/0.35/0.4）均稳定在 1/6；
- 五笔权重 0.2→0.4 把临界对（解/角 0.56→0.54、超/赵 0.56→0.54）压过阈值线，且不降召回。

## 阈值

`SAFE_CHARACTER_SIMILARITY` 保持 0.55：

- 降到 0.5：不应混淆超标升至 5/6（大量形近异字被放行，违背"不误绑"）；
- 升到 0.6：应纠达标从 23 降至 19，得不偿失。

## 已知盲区

- 姬/姫：四角（4141/4141）、仓颉（VSLL/VSLL）、五笔（VAHH/VAHH）全同码，任何形码方案都无法区分；姫 不在词表，端到端自动纠回正确，无需特判。
- 季/李：三维全高（0.75/0.75/0.67），单字层 0.72 超标；但端到端「李布」场景 top1 正确（margin 0.57），名称场景不会误绑。
- 嬴/赢：五笔同码 YNKY（与四角同码 0021/0021 一致），多维仍偏高（约 0.82）；OCR 场景靠候选唯一/匹配字主导纠对。

## 实现说明

- 五笔码表：`src/data/wubi86.txt`，UTF-8/LF/无 BOM，`字<TAB>码`，仅 GBK 内 3-4 码全码（20903 字）。来源：lxgw/wubi86-super（RIME 单字 86 全码表），取每字最长码，过滤非 GBK 与码长非 3-4 的条目。
- 缓存：`char_info_cache.json` 增加 `wubi` 字段；`scripts/build_character_feature_cache.py` 会对缺失该字段的缓存字重建。
- 降级：码表缺失或字不在码表时 `wubi` 为空，该维度记 0 分，不触发权重重归一，不影响其余维度。
- 更换码表版本（86→98 或不同来源）后，需重跑本文档的评测方法复核权重与白名单。

## 缓存分层（基线 + 用户层）

- 基线：`src/data/char_info_cache.json` 入库，保证确定性与 CI 契约测试（`tests/test_ocr_components.py` 校验覆盖当前武将名与常见误识字）。
- 用户层：`data/char_info_cache.json`（gitignored）。运行时 `get_feature`/`warmup_characters` 动态构建的缺失字符会原子写入用户层，下次启动加载时自动合并（用户层覆盖基线）。
- 新增武将后无需手动操作：识别预热按当前 `heroes.json` 武将名自动补齐并落盘用户层；仅在武将数据提交时重跑 `python scripts/build_character_feature_cache.py` 同步基线，CI 契约测试会拦截遗漏。
