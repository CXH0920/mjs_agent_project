> 状态：阶段一（B2 复核模式）已实施（2026-09-19）；阶段二（B1 全量切换）由阶段一数据触发，暂不实施

## 一、背景与问题

### 1.1 三个原始痛点

1. **选将页王濬只识别一个字**：OCR 输出「王」，候选闭包 6 个王姓武将，长期待人工确认。
   根因有两层（详见 §二）：①「濬」不在 PaddleOCR 简体识别字典 `ppocr_keys_v1.txt`（6623 字）中，
   识别头结构上无法输出；②王濬名条（西晋主题银灰色）下段白字压近白底，第二字连检测框都拿不到。
2. **对局攻略卫玠待确认**：错读「卫珍/卫珑」落点多候选（卫玠/卫青），三路证据置信度 0.61~0.67
   低于多候选决胜门槛 `_MULTI_CANDIDATE_MIN_CONFIDENCE=0.7`，白名单对「珍→玠」无从发挥。
3. **官方数据导入的兜底链负担**：简体字典缺字导致 名字 cell 需 cht 繁体引擎兜底 + glyph 逐字切分 +
   榜单唯一性补全 + 待复核 CSV 一整套绕行机制（提交史 `06f03cb`/`8b8a3d5`/`2fcd55f`）；
   cht 兜底还引发过「卫玠跨候选误绑周瑜」事故（`8b8a3d5` 修复为 allowed_names 受限模式）。

### 1.2 词表-字典缺口盘点（评估的出发点）

对 `data/heroes.json` 184 个武将名逐字核对简体识别字典，**字典外字符 10 个、涉及 10 个武将**：

| 字 | 武将 | 简体字典(6623) | 繁体字典 cht(8419) | ppocrv5 字典(18383) |
|----|------|----------------|--------------------|---------------------|
| 勖 | 荀勖 | ✗ | ✓ | ✓ |
| 哙 | 樊哙 | ✗ | ✗ | ✓ |
| 惇 | 夏侯惇 | ✗ | ✓ | ✓ |
| 濬 | 王濬 | ✗ | ✓ | ✓ |
| 玠 | 卫玠 | ✗ | ✓ | ✓ |
| 眜 | 钟离眜 | ✗ | ✓ | ✓ |
| 磾 | 金日磾 | ✗ | ✓ | ✓ |
| 芈 | 芈八子 | ✗ | ✗ | ✓ |
| 逖 | 祖逖 | ✗ | ✓ | ✓ |
| 郃 | 张郃 | ✗ | ✓ | ✓ |

其中 5 个（勖/哙/惇/眜/芈）已被基线白名单的确定性错字对覆盖
（`助/歇→勖`、`会→哙`、`怀→惇`、`昧→眜`、`半→芈`——机制为「引擎稳定读成字典内错字 → 白名单纠正」）。

### 1.3 关键前置教训：chinese_cht 繁体兜底不可行（实测）

繁体字典虽含 濬/玠，但权重不认识（渲染完美白字黑底直喂：`濬→溶(0.99)`、`玠→珍(0.88)`、`衛→偉`、`卫→无输出`）。
真实裁剪 4 样本全错，且「衛玠→門瑜/工瑜」的读数在候选闭包中**唯一命中周瑜**——即 7 月误绑事故的机理复现。
结论：**字典覆盖只是第一道门槛，「权重是否认识」必须实测**（该验证协议已沉淀，见 §七）。

## 二、根因分析：三层失效模型

1. **图像层**：名条底色随阵营主题（西晋最浅）、竖排两字、选将页 ROI 仅 50×145。
   白字压浅底时低对比度区域的笔画信号弱。
2. **字典层**：字典外的字在 CTC 输出空间中不存在，只能「整字消失（blank）」或「字典内形近替身」。
   实测同一武将在不同喂法下的替身：濬 → 无/睿/潜；玠 → 珍/瑜（渲染字实验，
   paddle 3.x 管线在竖排渲染上按字分框可读对 `王(0.9998)+濬(0.9339)`，证明是权重认识问题而非算力问题）。
3. **决策层**：候选闭包由编辑距离 ≤1 构成，白名单只做「等长差一字」的评分加成（1.0），
   不收窄候选、也撬不动多候选决胜的 0.7 置信度门槛——截断（漏字）形态在结构上无法被白名单表达。

## 三、候选方案与验证结论

### 3.1 方案清单

| 方案 | 结论 |
|------|------|
| A 维持现状 | 人工确认 + 错法频次沉淀；对 10 字中的 5 个已闭环（白名单对） |
| B1 paddle 3.x 全量替换 v5/v6 | 依赖升级（paddleocr 3.x + paddle 3.x）+ 全量回归，体积 +200M |
| B2 目标式复核引擎 | 主引擎不动，新引擎只对未决槽、且读数必须落在候选闭包内（8b8a3d5 纪律） |
| C 自定义字典微调 | 扩字典迁移训练，治本；约一周工作量 + 训练设施 + 长期维护义务 |
| D 名条模板匹配 | 逐武将打补丁；判别力验证未做（同阵营背景同化风险） |
| **ONNX 部署形态** | **B1/B2 的部署载体**：RapidOCR + onnxruntime，卸载 paddle 全家桶，净减 230M |

### 3.2 cht 繁体模型：排除（实测 0/4 + 渲染字失败，见 §1.3）

### 3.3 版本对比（v4 / v5 / v6-small，统一 RapidOCR+ONNX 栈、画布喂法、`Det.limit_type=max`）

**准确率**：

| 指标 | v4（=生产权重 ch_PP-OCRv4_rec） | v5 mobile | v6-small |
|------|------|------|------|
| 素材门槛（29 张：渲染字+真实裁剪） | 12/29，EMPTY 5 | 22/29，EMPTY 2 | **27/29，EMPTY 0** |
| 官方榜探针（7 个生僻字武将） | 4/7 | 7/7 | **7/7（置信度最高）** |
| 选将 84 图 raw 与生产分歧 | 12（全为生僻字盲区） | 43 | 42（**好 35 / 坏 7**） |

**v6-small 独有突破**：王濬两个真实裁剪**直读正确**（0.9975/0.9967，生产截断、v5 读成王睿）；
荀勖直读置信 0.9768/0.9661（v5 为 0.84/0.72）；金日磾 0.9906；芈直读正字（v5 输出繁体羋）。

**v6 新错法（7 处，全部单字/截断级，可走纠错层）**：公孙瓒→瓚（繁体异体 ×5）、赵婕妤→好（×1，同字位另有读对样本，存在摇摆）、张郃→邻（×1）。
另有低频：卫玠单裁剪 → 卫酚（同批画布读法又正确 0.69）、眜→眛（异体）。

**速度（84 图画布批量，稳态中位）**：v4 497ms / v5 552ms / **v6-small 598ms**（同栈内 v6 慢 20%，见 §五分模块口径）。

**体积（模型）**：v4 15.5M / v5 21.4M / **v6-small 31.1M**（v6-medium 134M，越界不评）。

### 3.4 v6-small 部署形态正面对比：paddle 3.x 原版管线 vs RapidOCR/ONNX（实测）

同一份 v6-small 权重，两种运行时、同协议（29 门槛 + 官方探针 + 84 图画布批量）：

| 形态 | 素材门槛 | 官方探针 | 84 图批量稳态中位 | 依赖体积 |
|------|----------|----------|--------------------|----------|
| **paddleocr 3.7 + paddle 3.3.1（mkldnn 关闭）** | 27/29（卫盼/眛） | 7/7（0.994~1.0） | **1971.5ms** | paddle ~350M + paddlex 链 ~155M |
| **RapidOCR 3.9 + onnxruntime 1.23** | 27/29（卫酚/眛） | 7/7（0.997~1.0） | **598.2ms** | onnxruntime 41M + rapidocr 32M |
| （参照）生产 2.x 管线 | 12/29 | 4/7 | 642ms（含回退） | paddle 280M + 4M |

两个决定性发现：

1. **paddle 3.3.1 的 oneDNN 与 v6 det 模型不兼容**：开启 mkldnn 即抛
   `NotImplementedError: ConvertPirAttribute2RuntimeAttribute not support [pir::ArrayAttribute<pir::DoubleAttribute>]`
   （PIR 格式模型 + oneDNN 指令转换缺陷）；禁用 mkldnn 后可运行，但 CPU 推理退化为 **1971.5ms/页，
   是 ONNX 形态（598.2ms）的 3.3 倍、生产现状的 3 倍**。
2. **精度完全等价**：两种运行时门槛同为 27/29（失败样本集合有单字级差异——卫盼 vs 卫酚、均为运行时数值差异的边缘翻转），探针同为 7/7。

结论：**v6-small 权重下，ONNX 形态在速度（3.3 倍）、体积（-230M vs +200M）、依赖面三个维度全面占优，精度无差异**。
paddle 3.x 路线仅在「paddle 修复 PIR/oneDNN 兼容问题」或「官方提供非 PIR 导出」后可重新评估；
v6-medium 经 paddle 管线实测 8635.6ms/页（mkldnn 关闭口径），CPU 场景不可用，维持不评。

## 六、优化空间与必改点

### 6.1 官方导入改「rec-only 逐 cell」——实测 7.7 倍（最大优化点）

官方榜单的 cell 是横排单行印刷体，网格坐标已知，**无需逐 cell 跑 det**。
实测：det+rec 逐 cell 111.2ms/call → **rec-only 14.5ms/call，整页 22.2s → 2.9s**（比现状 14.8s 快 5 倍）。
实现：每页 1 次整页 det 取文本坐标（或沿用网格切割坐标）→ 逐 cell 只跑 rec。

### 6.2 必改点：det 缩放参数（不改必挂）

RapidOCR det 默认 `limit_type=min, limit_side_len=736` 会把短边不足 736 的图强制放大：
150×435 名条被放大 4.9 倍（单字高约 1000px，冲出 DBNet 工作尺度）→ 概率图碎片化/消失。
**v5 det 在该默认参数下 29 素材 26 张检测为空；v6-small det 对同一预处理稳健（默认参数 0 空框）**。
工程纪律：`Det.limit_type=max, Det.limit_side_len=960` 作为引擎配置**显式写死**（不依赖默认值），
并把「喂法形状 × 分辨率」矩阵纳入验证协议；单槽回退路径若存在，须同样过该配置。

### 6.3 其他优化项

- **int8 量化**：动态量化在 det 上不可用（`ConvInteger` 未实现）；需静态量化（QDQ+校准集）。
  rec 21.2M → 5.3M（实测转换产物），速度收益未验证。列为可选项。
- **ORT 线程**：intra_op=12 实测劣化（默认已优），预期收益 <10%。
- **画布并行**：CPU 已是瓶颈，收益有限。

## 七、验证协议（沉淀为标准流程）

任何新识别引擎/模型接入前必须过两道门槛 + 一轮回归：

1. **字典覆盖**：核对全部武将名字符在识别字典中（文本检查）；
2. **权重实测**：渲染字（白字黑底，隔离图像变量）+ 真实裁剪逐张判定——chinese_cht 死于第二道；
3. **全量对照**：四环境测试图按生产同构喂法（画布、动态 ROI）逐槽 raw 对照生产引擎，
   分歧逐条分类（更好/更差/待核验），必要 时视觉核验裁剪；
4. **白名单治理**：新错法补对、失效对退役（参照 `9ca1b91` 的退役重放法）；
5. **回归底线**：已决槽零退化、未决集合不扩大。

## 八、推荐方案与实施路径

**推荐：v6-small + RapidOCR(ONNX) 部署形态**（四环境全量数据支撑，王濬/卫玠/荀勖/金日磾/羊祜等未决槽直读修复，官方导入生僻字 25 处直读增益）。

分两步落地（B2 先行，爆炸半径最小）：

1. **阶段一（B2 复核模式）**：主识别管线不动；新增 RapidOCR/v6 引擎，仅对未决槽
   （resolution ∈ unresolved/conflict 且候选闭包非空）做画布复核，读数必须落在候选闭包内才采纳
   （作为 `source="rare_recheck"` 证据追加，走既有多候选门槛）。
   落点：`OcrWorker._rare_char_ocr_engine` 槽位（已存在）、`_append_single_name_evidence` 扩展点、
   `paddle_loader` 适配层（RapidOCR 输出 → 2.x 风格结果）。
2. **阶段二（视阶段一数据决定 B1）**：主引擎全量切换 v6-small；同步白名单治理
   （新错法对：瓚→瓒、嬴→? 等按重放结果定；退役 v5/v6 直读导致失效的 对），阈值重校
   （0.7/0.995/0.55/0.75 按新置信度分布），官方导入 cht 兜底子系统退役。

**工程量**：B2 约 300~400 行（适配层 + 复核插槽 + 配置）+ 回归半天；B1 另加 spec/release 改造与全量重放。
**体积**：ONNX 路线净 -230M（卸 paddle 280M + paddleocr 4M，装 onnxruntime 41M + rapidocr 32M + 模型 31M）。

## 九、风险清单

1. **第三方封装**：RapidOCR 版本节奏与接口变化需跟随（当前 3.9.2 实测通过；结果对象结构在各小版本有差异，适配层需保留防御性兼容）；
2. **数值分歧常态化**：ONNX 与 paddle 的 0.9% 低置信分歧，每次模型/引擎更新需重跑对照协议；
3. **det 参数-尺度耦合**：默认参数对小图不安全（v5 实证 26/29 空框；v6 稳健但不宜依赖），参数必须显式写死并纳入协议；
4. **喂法形状覆盖**：任何新喂法（如单槽回退）都需按 §七 协议单独验证；
5. **白名单治理窗口**：切换期新旧错法并存，待复核率可能短暂波动；
6. **模型成熟度**：v6 于 2025 末发布、RapidOCR 3.9 集成，社区沉淀时间短于 v4/v5。

## 十一、推理设备决策：GPU 评估（v6-small-ONNX 是否启用 GPU）

### 11.1 历史复盘（git 提交史）

| 时间 | 提交 | 内容 |
|------|------|------|
| 08-04 | `9cebee4` | 启用 PaddlePaddle GPU 推理（CUDA 11.8 + cuDNN 8）；同提交已出现「防止多实例同时占用 GPU 引发偶发加载失败」的防护，并将 OCR 预热前置到启动画面（规避 Paddle 初始化持 GIL 界面卡死） |
| 08-17 | `ac8bee5` | 「修复 GPU 推理异常导致的整机卡顿」：新增 `MUMU_OCR_USE_GPU`（默认 false 走 CPU）与 `MUMU_OCR_CPU_THREADS=6`，CPU 模式启用 MKLDNN 并限线程；同步等待 30s 超时（防 GPU 驱动异常时调用线程无限阻塞）、引擎加载失败熔断、轮询连续失败自动暂停 |

GPU 启用到回退共 13 天。

### 11.2 本机硬件现状（决定性约束）

RTX 2070 8GB 单卡，显示器直连（`Disp.A: On`），桌面合成器 + MuMu 模拟器渲染 + OCR 全在同一块卡上。
实测 `nvidia-smi`：**显存 7205MiB / 8192MiB（88% 已占用，余量约 1GB）**，且随游戏场景波动。

### 11.3 冻结机理

1. OCR GPU 推理并非零成本借用：CUDA Context + cuDNN workspace 数百 MB 常驻，推理时临时缓冲反复分配，
   cuDNN 自动调优阶段产生长时间独占计算；应用内多页型识别器多实例时上下文互相踩踏（`9cebee4` 当天已现）。
2. 显存接近满载 → WDDM 把 resident 页面换出到共享内存（每次换页均为 PCIe 往返，游戏渲染与桌面合成
   的所有队列一起停）→ 分配超时触发驱动重置（TDR）→ 整机冻结。
3. OCR 是轮询常驻负载（1~2s 一次），每次轮询都在挤兑边缘反复横跳，冻结反复出现。

**根因是资源挤兑，不是 paddle 框架缺陷**——换 onnxruntime 不改变「往已饱和的 GPU 上加推理负载」的本质。

### 11.4 v6-small-ONNX 启用 GPU 的评估

| | CUDA EP（onnxruntime-gpu） | DirectML EP（onnxruntime-directml） |
|--|--|--|
| 运行时依赖 | CUDA 12.x + cuDNN 9 严格配版本，nvidia-* 系列 +1~3GB（ONNX 的体积优势蒸发） | DX12 即可，+100~130M |
| 显存行为 | Context + workspace 数百 MB 常驻 | WDDM 管理，与游戏挤兑本质相同 |
| 多实例 | 每 session 独立 context，历史教训原样适用 | 同样争用 |

**收益上限**：598ms 画布批量中，画布构建/resize/归一化/CTC 解码/坐标映射均在 CPU；
即使 GPU 把模型计算段提速 5 倍，总时长下限被 pre/post 钳制约 300~400ms——**收益封顶 1.5~2 倍**。
而四模块节拍现状（选将 598 / 对局 325 / 巅峰 776 / 官方 rec-only 后 2.9s/页）已全部满足需求，GPU 无必要。

### 11.5 假设性开启的前置条件（本机当前不满足）

1. 显存余量 ≥2GB 且全程稳定（本机余量约 1GB 且随场景波动——**否决项**）；
2. CUDA 路线：onnxruntime-gpu 与 CUDA 12.x + cuDNN 9 严格匹配；DirectML 路线：`onnxruntime-directml`；
3. 保留 `ac8bee5` 三层防护（30s 超时 / 加载熔断 / 轮询暂停），新增 VRAM 预检（可用显存低于阈值自动回退 CPU）；
4. 仅 B2 复核场景启用（偶发调用），绝不进轮询热路径；应用内单引擎实例，杜绝多实例争用。

### 11.6 结论

**v6-small-ONNX 不启用 GPU**：冻结风险与历史完全同源（资源挤兑，与框架无关），本机显存 88% 占用
比历史事故时期更紧；收益封顶 1.5~2 倍且仅作用于计算段；`ac8bee5` 的 CPU 默认是对「OCR 与游戏共享
一块 GPU」这一硬件现实的正确适配。GPU 作为「显存充裕机器上的可选优化」保留本节记录，
重新评估触发条件：更换显存 ≥12GB 的独立显卡，或 OCR 独占 GPU 的部署环境。
