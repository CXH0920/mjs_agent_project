## 一、真机取证结论

### 1.1 窗口特征（R1 窗口识别规则定稿依据）

| 项 | 值 |
|---|---|
| 进程名 | `mjs.exe` |
| 窗口标题 | `名将杀`（固定，无动态后缀） |
| 窗口类名 | `UnityWndClass`（Unity 标准窗口类） |
| 渲染引擎 | Unity（随进程运行 `UnityCrashHandler64.exe`） |
| 窗口样式 | 常规重叠窗口（EXSTYLE=0x100，无 LAYERED/NOREDIRECTIONBITMAP，非 Cloaked） |

识别规则：**进程名 `mjs.exe` + 类名 `UnityWndClass`** 双条件匹配（标题仅展示用，不作为匹配键——标题可被同名进程伪造，进程名+类名组合已足够唯一且稳定）。

### 1.2 采集手段实测（选型依据）

对运行中客户端窗口逐一实测（三脚本、多轮重试）：

| 手段 | 结果 | 判定 |
|---|---|---|
| PrintWindow（PW_RENDERFULLCONTENT 0x2 / +CLIENTONLY 0x3，重试 3 次） | **稳定返回 0（调用失败）** | 不可用。窗口样式无异常（无 NOREDIRECTIONBITMAP、非 Cloaked），失败根因未深究，事实以实测为准 |
| 原生 BitBlt 全虚拟屏 → 客户区裁剪 | ✅ 出图正常（2560×1361，灰度均值 90，无黑帧），人工确认画面完整无遮挡残留 | 可用（兜底） |
| Windows.Graphics.Capture（经 `windows-capture` 库） | ✅ 出图正常（2560×1390 含标题栏，灰度均值 111），人工确认完整游戏画面 | 可用（主路径） |
| Pillow `ImageGrab` 全屏裁剪 | ❌ **坐标系陷阱**：Pillow 内部切换线程 DPI 上下文，混合 DPI 多屏下其图像坐标与窗口物理坐标错位，实测裁错窗口 | 不可用（实现必须自写 GDI BitBlt，不得经 Pillow 抓全屏） |

### 1.3 DPI 事实（混合 DPI 双屏实测）

- 进程未声明 DPI 感知时，系统对副屏（125%）窗口**谎报坐标**：客户区报 2048×1088（逻辑值），真实 2560×1361（物理值）。
- 声明 Per-Monitor-V2 后坐标恢复物理像素，三种采集手段坐标系统一。
- **结论：进程级 Per-Monitor-V2 声明为硬前置**（启动时一次 `SetProcessDpiAwarenessContext`，或 PyInstaller manifest；GUI 为 PySide6，Qt 自身声明 DPI 行为需实测确认是否与手动声明一致，以实测为准）。

## 二、选型决策

### 2.0 WGC 会话必须句柄定向（2026-10-26 真机事故修订）

初版实现按窗口标题连接 WGC（`window_name`），真机使用即翻车：库的标题匹配是
**子串匹配**，而工具自身主窗口标题"名将杀 Agent"包含"名将杀"，用户点连接时
工具窗口必在 Z 序顶端，WGC attach 到工具自身窗口，截出的是工具 UI（实测
1093×754 = 工具客户区，且带光标——初版 `cursor_capture=None` 走库默认开启）。
游戏标题的任何子串均为工具标题子串，字符串层面无解。

修复三件套：

1. **`window_hwnd` 句柄定向**（根治）：库 2.0.1 原生支持，直接绑定枚举所得
   游戏窗口句柄；原"多实例退 BitBlt"限制一并解除（任一窗口均可定向）。
2. **`cursor_capture=False`**：OCR 采集不带光标（光标悬停遮挡 UI 影响识别）。
3. **帧尺寸对账防线**（纵深）：裁剪时 WGC 帧尺寸须与目标窗口可见边框一致
   （容差 32px，真机取证两者精确吻合），不符即丢帧走兜底——任何未知形式的
   错误 attach 被尺寸差拦截，截错窗口的画面不得作为成功结果返回（显示诚实）。

4. **BGRA→RGB 通道反转**（2026-10-26 第二起真机事故）：库的 frame_buffer
   是 Direct3D **B8G8R8A8** 纹理内存（库的 save_as_image 走 cv2 BGR 约定故
   正确，直接消费必须自行反转红蓝）。初版按 RGBA 读，游戏暖色调整体偏蓝紫；
   此前未被取证发现是三重巧合叠加——取证走 save_as_image（正确路径）、灰度
   统计对通道互换不敏感、API 对比实验的对照像素恰为灰色边缘阴影。
5. **回退路径左阴影自校准**：DWM 边框查询失败时回退窗口矩形，而 Win10 窗口
   矩形左右各含约 7~9px 不可见阴影（上边为 0）——此前直接用矩形左上导致横向
   裁剪偏大一个阴影宽、右侧缺约 7px（真机实测 1687 vs 1694、1913 vs 1920）。
   修正为 `rect.left + (rect_w - frame_w) // 2`（帧宽在手，阴影左右对称，
   魔法数变自校准计算）；垂直方向上边阴影为 0，矩形顶即帧顶。

附带事实：该 Unity 窗口的 `DWMWA_EXTENDED_FRAME_BOUNDS` 查询**稳定失败**
（E_INVALIDARG，非 Cloaked），帧尺寸对账在 bounds 可用时生效、不可用时退
窗口矩形估算并保留"半宽丢弃"守卫。

### 2.1 主路径变更说明

原方案推荐 PrintWindow 主路径（全版本一致），并预留决策树分支："若真机取证发现 PrintWindow
截不出来，WGC 为备选救兵，Win10 1903 以下退回全屏裁剪"。**真机取证走了该分支**：
PrintWindow 对本客户端稳定失败，主路径变更为 WGC，原兜底（BitBlt 客户区裁剪）不变。

### 2.2 定稿链路

```
截图请求
  → 前置检查：窗口仍存在？（销毁 → 按未启动报错）最小化？（→ R4 报错）
  → 主路径 WGC（Win10 1903+，windows-capture 库）
      合成器级窗口帧 → 客户区裁剪（DWM 可见边框与客户区原点差值）→ 黑帧检测
  → 主路径不可用（系统 <1903 / 会话创建失败）或黑帧
      → 兜底 BitBlt 客户区裁剪（要求窗口可见；被遮挡部分截不到）
  → 仍黑帧/失败 → 按 R4 文案报错（全屏黑屏引导切窗口化 / 请还原窗口）
```

- 黑帧检测：灰度均值与近黑像素占比双指标（取证实测正常画面均值 90~111、暗占比 ≤7%；
  检测阈值取"均值 < 8 且近黑(亮度<16)占比 > 0.98"，与既有 image_validation 惯例对齐后定稿）。
- 采集方式选择对用户无感（R2.4），实现于模块内部，不暴露配置项。

### 2.3 版本兼容语义

| 系统 | 行为 |
|---|---|
| Win10 1903+ / Win11 | WGC 主路径（遮挡可采集；2004+ 可去捕获边框提示） |
| Win10 1803~1809 / Win8.1 | 自动退 BitBlt 兜底（窗口须可见无遮挡，启动时一次性说明提示） |
| Win7 / Win8 | 不承诺（需求文档第七节） |

实现以运行时探测（WGC 会话创建成败）决定路径，**不解析系统版本号写分支**——探测即降级，
一套代码覆盖，无版本号适配面。

## 三、依赖与集成变更

1. **新增依赖 `windows-capture`**（Rust 扩展，cp311 win_amd64 wheel，已真机验证出图）。
   理由：WGC 的 WinRT 互操作样板（D3D11 设备互操作 + 帧池 + surface→纹理拷贝）自写约 200+
   行且未经真机验证；该库封装后 API 面极小。登记入 `environment.yml` / `environment-ci.yml`。
2. 采集帧经回调线程持续刷新至"最新帧"缓冲，截图请求（低频 OCR 语义，与模拟器 screencap
   同构）直接取最新帧——避免为按需截图做会话启停编排。
3. 窗口枚举（EnumWindows + 进程名/类名匹配）纯 ctypes 实现，无新依赖。
4. 下游管线零改动：模块对外对齐 `AdbCapture.screencap_full()` 形态（`(bool, PIL.Image | str)`）。
