# UI 层架构规范

> 长期设计规则与决策依据，覆盖主窗口、对话框体系、服务通信模式。

## 一、架构模式：业务服务 + Qt 信号

### 规则 1.1：业务逻辑不持有 UI 引用

所有业务服务（`*Service` 类）继承 `QObject`，通过 `Signal` 与主窗口通信，不持有 `MainWindow` 或任何 `QWidget` 的引用。

```
CaptureService —Signal→ MainWindow —slot→ 更新 UI 或弹窗
OcrService    —Signal→ MainWindow —slot→ 启动/停止轮询
```

**为什么：** 如果业务服务持有 UI 引用，单元测试时需要构造完整的 Qt 组件树。信号槽解耦后，测试只需 assert 信号发射的参数是否正确，无需实例化 `QMainWindow`。这也是 Qt 框架推荐的设计模式。

### 规则 1.2：OCR 任务必须进入唯一后台 worker

模板匹配和 PaddleOCR 识别必须提交到 `OcrWorker` 的单线程队列；官方榜单导入必须作为一个不可拆分的整批任务进入同一队列。worker 只能通过信号把结果交回 GUI 线程更新界面。`QTimer.singleShot(0, ...)` 只用于延后回调，不视为异步执行方案。

**为什么：** PaddleOCR 单次识别可能耗时数秒。单 worker 保持现有 A → B → C 的串行顺序，同时避免手动识别和轮询路径在不同线程直接使用同一识别器。ADB 截图仍是独立的同步步骤，不属于本规则的迁移范围。

### 规则 1.2.1：识别 ROI 与页面模板独立缩放

武将名称默认 ROI 固定以 2560×1440 为参考尺寸缩放；页面模板的参考尺寸只用于模板匹配，不能作为武将 ROI 的缩放依据。

**为什么：** 用户可在 1920×1080 制作页面模板，再导入 2560×1440 截图。若复用模板参考尺寸，末尾名称 ROI 可能越出画面并传入空图给 OpenCV。

### 规则 1.2.2：共享截图服务的回调只由发起页面消费

选将推荐和对局攻略共用 `CaptureService` 时，页面收到 `capture_completed` 后必须先检查自身是否存在待处理请求；没有待处理请求必须直接返回。

**为什么：** Qt 信号会广播给两个页面。没有来源保护时，对局攻略的图片导入会错误刷新选将推荐页面。

### 规则 1.3：轮询定时器不自杀

轮询触发时如果条件不满足（如 ADB 未配置、模板未加载），应 `return` 等待下一次 tick，而非调用 `stop_poll()` 永久停止。

**为什么：** `stop_poll()` 会杀死定时器，唯一重新激活的入口是用户再次打开配置对话框。如果用户远程操作或条件临时变化（如模拟器未启动），程序需要能自动恢复。自杀逻辑导致"用户配置好了一切，但轮询永远不会启动"的 bug。

### 规则 1.4：轮询只在 ADB 已连接时运行

即使配置启用了持续轮询，应用启动、设备未连接、切换设备或连接断开时也必须保持轮询定时器停止；仅当 `CaptureService` 状态变为 `connected` 后才启动轮询。

**为什么：** 轮询线程不应在未连接状态下主动竞争 ADB 连接或执行截图，否则用户在模拟器配置界面切换设备时，可能与连接流程并发产生空截图或截断截图。

## 二、对话框体系

### 规则 2.1：BaseHeroSelectDialog 控制选择行为

所有武将选择对话框继承 `BaseHeroSelectDialog`，通过 `SelectionMode` 枚举控制单选/多选/数量限制。不使用 QDialog 的直接实例化。

**为什么：** 武将选择逻辑在多个地方复用（获取指定武将、指定攻略生成、相性配对、选定武将相性）。如果每次独立实现，会导致搜索/筛选/复选框逻辑重复 4 遍。基类统一了这些逻辑，子类只需指定模式和返回格式。

### 规则 2.1.1：多选结果独立于当前筛选列表

多选对话框必须以武将 ID 集合保存已选结果；搜索、势力筛选和列表重建只能改变当前可见项，不能清空或改变未显示的已选结果。界面显示“全选当前筛选”“清空已选”、已选数量和可删除的已选标签；势力筛选右侧箭头必须随弹窗状态在向下（收起）与向上（展开）之间切换；确认按钮根据当前任务显示实际动作与数量。

`GuideFetchDialog` 的确认按钮显示“生成 N 篇攻略”。`SynergyPairDialog` 限制选择 2~8 名武将，并实时显示 C(N,2) 总组合数、已有组合数与本次待生成组合数。相性对默认跳过已有记录，用户可显式选择“重新生成并覆盖”；该选择必须传递到 CLI 的 `--update` 参数。

**为什么：** 多轮筛选是批量任务的常规操作。将勾选状态绑定到可见列表会导致用户无感丢失选择；相性组合数量会随 N 二次增长，必须在任务启动前明确展示实际工作量和覆盖后果。

### 规则 2.2：对话框不直接修改数据源

对话框对业务服务的调用仅在 `accepted` 后触发，不在对话框内嵌 `exec()` 的同时启动异步操作。

**为什么：** 对话框 `exec()` 阻塞事件循环。如果在对话框内启动 `QProcess` 并在 `finished` 时更新 UI，会因为事件循环被阻塞导致信号丢失或 UI 更新延迟。正确的顺序是：`dialog.exec()` → `accepted` → 退出阻塞 → 启动服务。

## 三、推荐面板数据流

### 规则 3.1：OCR 置信度不映射为推荐置信度

`update_recommendations()` 中 `card.set_confidence(0.5)` 固定值。

**为什么：** OCR 置信度反映的是"图像识别准确率"，而非"该武将的阵容适配度"。把 OCR 置信度直接当作推荐指数会误导用户——高识别置信度不等于高推荐价值。固定 0.5 表示"来自截图识别"，与 AI 生成的推荐指数（0~1）区分。

### 规则 3.2：选中武将的相性/胜率按名称加载

`_load_synergies_by_name(card_idx, hero_name)` 和 `_load_win_rate_by_name(card_idx, hero_name)` 使用武将名称查询，而非 index。

**为什么：** OCR 返回的是 `{index, name}`，其中 index 表示 8 个槽位的位置（1-8），不反映数据库中的英雄 ID。通过名称匹配到 `Hero` 对象后再获取 ID，进而查询 `SynergyManager` 和胜率 CSV。

### 规则 3.3：未匹配的武将名仍显示名称

```python
card.set_unrecognized_name(name, confidence)
```

**为什么：** OCR 识别出的名称即使不在 HeroManager 中（新武将或识别错误），也应显示给用户看，方便人工判断。如果直接清空或显示"空"，用户无法区分"没有识别到"和"识别了但不认识"。名称、置信度和空 Hero 状态由卡片公开接口统一维护，页面不直接操作卡片内部控件。

### 规则 3.4：推荐指数状态按异常提示，重建入口始终可达

推荐卡片在指数有效时以“推荐指数：分数 / 评级”格式显示，例如 `推荐指数：92 / S`，不显示“数据已更新”。官方榜单更新导致快照过期时，页面显示“推荐指数待重建”提示和“立即重建”按钮；“重建推荐指数”同时保留在“更多”菜单中，供用户修复数据后再次手动执行。

**为什么：** “数据已更新”容易被误解为 OCR 结果已经确认，而正常状态也不应重复占用卡片空间。过期提示需要足够醒目，但重建能力不能因为提示消失而丢失。

## 四、模拟器配置对话框

### 规则 4.1：共享 CaptureService 的 AdbCapture 实例

`MumuConfigDialog` 通过 `capture_service` 使用唯一的 ADB 会话，但不直接调用 `AdbCapture`；连接、断开、设备测试和模板截图均委托 `EmulatorOperationService`，再由 `CaptureService` 发布会话状态。

**为什么：** 如果对话框持有独立的 `AdbCapture`，而 `CaptureService` 也持有另一个，会出现"对话框中断开了，但截图按钮还在用旧连接"的状态不一致。共享引用确保了单点真相。

### 规则 4.2：制作模板 = 截图 + RoiSelector + 保存

模板制作流程固定：`EmulatorOperationService.capture_template_screenshot()` → `RoiSelectorDialog` → `OcrService.create_template()`。

**为什么：** 模板需要精确的 ROI 坐标来匹配游戏画面。如果只允许用户选择一张裁剪好的图片，用户难以精确定位 ROI 区域（不知原始分辨率下的坐标）。截图 + 拖拽框选可以在原始分辨率下精确定位。

截图、连接等共享 ADB 会话操作必须在操作服务的 ADB 后台线程中串行执行；设备探测使用独立后台线程，不能阻塞模板截图。MuMuManager 探测失败时应保留上次成功的设备选择。ROI 框选依赖鼠标事件，必须留在 UI 线程。

### 规则 4.3：按任务拆分配置导航

配置对话框使用“设备与连接”和“识别与自动化”两个左侧导航页，顶部固定显示共享 ADB 会话状态，底部固定显示取消和保存按钮。每个内容页可独立纵向滚动，但不得出现横向滚动。

识别页先展示全局 OCR 与轮询开关，再以“武将选择识别”和“对局攻略识别”两个任务面板分别收纳模板、匹配阈值和 ROI 操作；武将选择冷却仅显示在对应任务中。内容宽度不足时两个任务面板从双列自动切换为上下排列。

**为什么：** 设备连接与识别调参属于不同频率的任务。拆页可以降低单屏信息密度，而把模板和参数按识别任务聚合，可避免用户跨越“模板管理”和“识别参数”区块寻找对应项。响应式换列保证最低 760px 窗口和高 DPI 环境下仍可操作。

### 规则 4.4：仅在可处理时展示恢复操作

持续轮询关闭或运行正常时不显示“恢复轮询”；只有持续轮询已启用且服务处于暂停状态时才显示并启用。ADB 路径与模板文件名使用单行展示，完整路径通过 Tooltip 提供。

**为什么：** 长期显示不可用按钮会干扰主要配置流程，也无法向用户解释为何不可用。条件式操作能把暂停状态和可执行恢复动作绑定在一起。

## 五、全局样式

### 规则 5.1：势力色表从 JSON 配置加载

`_load_faction_colors()` 优先从 `config/faction_colors.json` 加载，文件不存在或格式错误时使用内建兜底色表。

```python
FACTION_COLORS = {
  "秦": "#8B4513", "汉": "#B22222", "楚": "#2F4F4F",
  ...
}
```

**为什么：** 游戏势力体系虽然已经稳定，但 JSON 配置文件让用户无需修改代码即可调整配色，也便于分享配色方案。内建兜底保证即使文件丢失程序也能正常运行。有模块级缓存，不重复读盘。

## 六、浏览列表选中恢复机制

### 规则 6.1：重建列表后恢复上次选中的项

`HeroListPanel` 在 `_refresh_list()` 中重建列表后，通过 `_last_hero_id` 优先恢复更改前的选中项，找不到时才回退到第 0 条。

```python
target_row = 0
if current_id is not None:
    for i, hero in enumerate(self._filtered_heroes):
        if hero.id == current_id:
            target_row = i
            break
self._list.setCurrentRow(target_row)
```

**为什么：** 编辑武将信息保存后列表会刷新重建。如果不恢复选中项，列表会自动跳到第 0 条，用户每次编辑完都需要重新滚动查找刚刚改过的武将。记录 `_last_hero_id` 并在重建后定位回来，用户感知不到列表的刷新动作——编辑完成后的视觉位置不变。

## 七、Tab 栏修改/删除按钮

### 规则 7.1：按钮放在 QTabWidget 角落而非 Tab 内容区

使用 `QTabWidget.setCornerWidget(widget, Qt.Corner.TopRightCorner)` 在 Tab 栏右上角放置按钮组，与页签文字同水平高度。武将信息 Tab 和攻略指南 Tab 各自对应一组"修改"+"删除"按钮，通过 `currentChanged` 信号切换可见性。

**为什么：** 用户要求"按钮与页签处于同一水平高度"。放在 Tab 内容区内（如 info tab 的头部）会占用内容区域的空间，且切换 Tab 时需要重新定位按钮。Corner widget 固定在 Tab 栏右侧，不随 Tab 内容滚动，且天然与页签同水平线。

### 规则 7.2：按钮颜色区分操作类型

修改按钮绿色（`background: #e8f4e8; color: #2e7d32`），删除按钮红色（`background: #fde8e8; color: #c62828`）。

**为什么：** 颜色是操作后果的第一视觉信号。绿色通行（安全操作）、红色警告（危险操作），用户无需阅读文字即可区分。两个按钮紧邻时，颜色差异降低误触概率。

### 规则 7.3：编辑使用独立 Dialog 而非内联编辑

`HeroEditDialog` 和 `GuideEditDialog` 是 QDialog 子类，以模态对话框形式打开。HeroEditDialog 包含所有 Hero 字段（名称/称号/势力/定位/体力/手牌/性别/难度），GuideEditDialog 包含所有 HeroGuide 字段（核心要点/新手提示/劣势对局类型/优势对局类型/搭配推荐/对抗建议/攻略正文）。

**为什么：** 内联编辑（直接让 QLabel 变为可编辑）会破坏只读浏览的正常体验——用户可能在查看时误触导致意外进入编辑模式。模态 Dialog 提供隔离的编辑环境，不影响浏览区的稳定性。

## 八、数据导入与推荐指数交互需求

### 8.1 官方数据导入对话框

“数据 > 官方数据导入”是 2v2 和放逐榜图片的唯一入口。两个有序图片列表可独立选择，也可同时选择；导入期间禁用重复提交与关闭，唯一 `OcrWorker` 按选择顺序串行处理整批任务。界面先显示排队/分析阶段的不定进度，检测到实际行数后展示精确进度；完成时显示每种数据的导入条数和待复核条数。主窗口只暂停原本活跃的自动轮询，弹窗退出后按连接和配置恢复，原本停止或暂停的轮询状态不应被强制启动。

UI 不得直接读取图片、切分表格或写 CSV；这些职责属于 `OfficialDataImportService`。失败时恢复操作控件、保留已选路径并展示可操作的错误原因。导入后的待复核项由文件和截图承载，首版不在此对话框内提供行编辑器。

### 8.2 推荐卡片的事实边界

推荐卡片可展示单将历史胜率、推荐分和 S～D 评级；展示值只读自已生成的快照。必须提供口径提示：“基于当前版本全服汇总数据计算，仅供参考”。

- OCR 置信度、推荐分、单将胜率是三个不同概念，不得互相换算或共用标签。
- 推荐指数快照待重建时，页面须显示中性状态提示；不得后台自动重建或以旧快照伪装为最新结果。
- “重建指数”必须经用户确认后执行；数据不足的武将展示“数据不足”，不参与奖牌、推荐排序或虚假的零分比较。
- 胜率前三名的视觉强调仅代表当前胜率快照排序，不代表推荐指数或阵容强度。

### 8.3 验收

- 两张导入图片可分别导入，单张失败不清空另一张既有数据。
- 导入完成、快照待重建、重建成功和重建失败均有清晰状态反馈。
- 相同快照下，推荐卡片显示的分数、评级、排序与数据层结果一致；卡片不自行重新计算指数。
