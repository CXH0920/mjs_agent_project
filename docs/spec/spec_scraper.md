# 爬虫与数据采集规范

> 长期设计规则与决策依据，覆盖官网 JS chunk 解析、数据清洗、Pydantic 校验链。

## 一、官网数据采集

### 规则 1.1：JS chunk 解析是唯一数据源

`fetch(BAIKE_URL)` → `find_chunk_url(html)` → `fetch(chunk_url)` → `extract_js_array(js_text)` → `js_to_json(text)`。

**为什么：** 官网百科数据通过 Nuxt.js 打包到 JS chunk 中，不提供 REST API。直接请求 API 端点会返回空或 HTML 结构而非 JSON。JS chunk 中的 `const e=[...]` 数组是结构最稳定的数据源，自项目启动以来格式未变化过。

上述解析规则集中在 `official_source/adapter.py`，对外由 `parse_heroes_chunk()` 提供单一入口。`tests/test_data/official_adapter/` 保存最小官网 HTML/JS 样本，契约测试用它验证适配器仍能定位 chunk 并解析原始记录。

### 规则 1.2：括号深度计数器替代正则提取数组

`extract_js_array()` 使用字符级遍历+深度计数器找到匹配的闭合方括号，而非正则 `r"\[.*\]"`。

**为什么：** JS chunk 中的数组可能嵌套对象、字符串中包含 `[` / `]` 字符。正则贪婪匹配会提前截止或跨越数组边界。深度计数器能正确处理嵌套结构。

### 规则 1.3：JS→JSON 三步转换是硬性预处理

`js_to_json()` 的三步操作顺序固定：
1. key 加引号 `a:1` → `"a":1`
2. `undefined` → `null`
3. 移除尾部多余逗号

**为什么：** 官网 JS 对象不是合法 JSON——无引号 key、`undefined` 值、数组/对象末尾的逗号，直接 `json.loads()` 100% 失败。三步操作分别解决这三个问题，顺序不可调换（例如先移除逗号再替换 `undefined` 会破坏 `undefined,` 的逗号定位）。

## 二、数据清洗（transform）

### 规则 2.1：id 和 name 缺失时跳过整条数据

```python
if hero_id is None: return None
if not name: return None
```

**为什么：** `id` 和 `name` 是所有后续操作（查找、展示、关联相性/攻略）的主键。如果缺失，这条数据在系统中完全不可用，保存只会污染数据文件。

### 规则 2.2：max_hp / max_hand 转型失败使用默认值 4

**为什么：** 官网数据中约 90% 的武将体力/手牌是 4，仅有少数武将（如华雄 6、袁绍 5）有特殊值。如果转型失败用 4，大概率是正确的；如果用 None，整个武将数据在校验阶段会失败。

### 规则 2.3：split_skill_desc 基于 HTML 结构拆分

按 `<p><strong>段标题</strong></p>` 识别段落，保留"技能描述"和"结算*"，丢弃"技能典故"和"设计思路"。

**为什么：** 官网的技能描述 HTML 结构固定。技能典故和设计思路是 lore 文本，对游戏策略无帮助，保留只会增加 AI prompt 的 token 消耗。

## 三、头像下载

### 规则 3.1：文件名使用武将中文名

头像文件路径为 `images/<name>.png`（如 `images/诸葛亮.png`），名称从官网原始数据的 `name` 字段提取。

**为什么：** 以中文名命名直接支持 UI 层的"按名称加载头像"逻辑，无需维护 `id → filename` 映射表。风险是同名武将的覆盖问题——名将杀中不存在同名武将。

名称必须经白名单校验：只允许中文、字母、数字、`_`、`-`，长度不超过 80，且不得是 Windows 保留文件名；不符合规则的头像跳过下载并记录 warning。

### 规则 3.2：仅接受受限的官网 PNG 图片

- 仅允许 `https://siteres.ztgame.com`，每次重定向都重新校验目标 URL，最多 3 次。
- 响应按 64 KiB 分块下载，最大 5 MiB；只接受 `image/png` MIME。
- 临时文件须通过 Pillow 的 PNG 解码和 4,000,000 像素上限校验，成功后原子替换 `images/<name>.png`。

**为什么：** 官网返回值属于外部输入。该限制防止异常 URL、过大响应或伪装/损坏图片写入本地，并保证失败时已有头像不受影响。

### 规则 3.3：单失败不影响整体

`download_hero_images()` 循环中单个武将下载失败只打 warning 不抛出异常，不中断其他武将的下载。

**为什么：** 165 个武将中个别头像链接失效是常见情况，整体流程不应因此中断。用户可后续重新运行查看差量。

## 四、需求范围、容错与验收

### 4.1 目标与范围

官网采集只负责恢复官网可提供的武将基础资料和头像：全量、增量、指定三种模式共享同一解析与校验链。官网结构、图片链接和文本均属于不可信外部输入；采集不生成攻略、相性、榜单排名或推荐指数。

### 4.2 容错边界

- 首页、chunk 定位或解析失败时，任务明确失败且不得覆盖现有 `heroes.json`。
- 单条关键字段无效时跳过该条并记录原因；辅助字段无效时按现有默认值恢复。
- 增量模式只合并本地不存在的 ID；指定模式只作用于用户指定目标，不得顺带清理无关武将。
- 头像下载失败、链接违规或图片校验失败不得中断数据采集，也不得损坏已有有效头像。

### 4.3 验收

- 最小 HTML/JS 样本可定位 chunk、解析嵌套数组并完成 JS→JSON 三步转换。
- 缺失 id/name 的记录不写入；体力或手牌异常的有效记录仍以默认值写入。
- 全量/增量/指定三种模式均通过 Pydantic 校验后再落盘；失败路径保留旧数据。
- 非法文件名、非 HTTPS/非白名单重定向、非 PNG、超尺寸或损坏头像均被拒绝并记录 warning。


## 五、公告监控与百科逐武将 diff

### 规则 5.1：公告数据源为公开 JSON API，HTML 仅作回退

```
GET https://ucmsv2api.ztgame.com/api/news/list?site=mjs&type=notice&page=1&per_page=5
```

单次请求返回 5 条公告全文（`code/data`，条目含 `id/title/content/publishdate/defaulturl`）。`fetch_latest_announcements()` 以 API 为主；API 失败时回退解析 `notice-1.html` 的 `<li>` 条目（仅 title/date/url，`content_missing=True`，不判相关）。

**为什么：** 公告列表页 `notice-N.html` 是 Nuxt 对上述 API 的 SSR 展示，逐篇爬详情页既慢又没必要；JSON 单请求约 1~2KB，比抓 340KB 的整页轻量得多。

### 规则 5.2：武将相关只认章节标题，不按正文提及的武将名判定

- 相关判据：正文（或标题）含 `【新增武将】` / `【武将调整】`（兼容 `【武将加强】【武将削弱】【武将修改】`）章节标题。
- 名称提取仅在对应章节内：`【新增武将】` 中独立成行的短名称 → “新增”；`【武将调整】` 中 `名称（增强|削弱|调整）` 或已知武将名 → 对应类型。
- 正文其他位置出现武将名（修复列表、副本内容，如“司马衷…调整为每回合限1次”“修复山涛…王元姬…联动”）**不判相关**：修复公告也常提到武将，且副本角色（如司马衷、贾南风）不在当前版本武将库，名称匹配会产生误报。
- 不在本地名单的名字一律标“未收录”（`known=False`），是否为本版本可玩武将由后续采集结果决定，不做臆断。

### 规则 5.3：延迟应对 = 百科逐武将 diff，不猜公告生效时间

公告发布通常早于实际生效，且官网百科数据滞后半天到一天。每次手动检查时：

1. 复用 `fetch_all_raw() → transform() → validate_heroes()` 获取清洗后的百科武将；
2. `hero_content_hash()` 仅基于官网字段（name/faction/position/max_hp/max_hand/gender/skills/icon_url，NFKC+去标签规范化后 md5），**不含**本地扩展字段（title/mode_viability/difficulty），保证与本地 `heroes.json` 同算法可比；
3. 与 `data/baike_snapshot.json` 逐武将比对，输出新增/修改/删除；
4. 公告提及且 diff 确认 → “可更新”；公告提及但 diff 未变 → “待生效”；diff 变化但无公告 → 仍提示“百科有更新”。

**快照初始化：** 首次启用优先用本地 `heroes.json` 各武将哈希建基线（手动编辑过的武将不会被误判为官网变化）；本地无数据时以百科为基线，不提醒。`mark_applied()`（采集完成后）将当前百科哈希写回快照，使差异归零、不重复提醒。

### 规则 5.4：频率约束与失败边界

- 仅手动检查，不轮询、不在应用启动时自动联网；每次检查最多 3 次请求（公告 API、回退 HTML、百科 chunk）。
- 两次手动检查最小间隔 60 秒（`CHECK_COOLDOWN_SECONDS`）；检查进行中或冷却期内再次点击会弹出提示，不发起请求，避免短时间密集请求触发官网风控。
- 公告 API 与百科获取失败只记日志并在状态栏提示，不中断应用、不覆盖旧快照、不误报“已更新”。
- `data/announcements.json`（按 url 去重）与 `data/baike_snapshot.json`（覆盖式）均不会无限增长。
- 删除类变更仅提示、不自动删除本地武将；更新动作使用“指定获取 + 增量”精准覆盖，不使用全量。
- **更新前必须经用户确认**：`build_update_candidates()` 组装候选（ready 公告解析武将 + diff 的 added/modified 并集），`hero_field_diff_summary()` 生成“本地 vs 官网”字段级差异摘要（定位/体力/手牌/技能描述等），确认对话框勾选要覆盖的武将；未勾选的保留本地内容。
- **保持本地基线**：首启用本地 `heroes.json` 建哈希基线；用户手动修正过的武将（本地≠官网）会被列为 modified，这是可接受的提示代价——确认对话框保证不会误覆盖。执行一次“更新武将数据”确认（含全取消）后快照刷新为当前官网哈希，官网未再变化即不再提示。
- **基线防污染**：快照为空时，仅当本地 heroes 文件不存在（全新安装）才允许以官网当前建基线；本地文件存在但解析/加载为空时**跳过基线初始化且不写快照**（否则 diff 恒空、新增/调整永不提示）。基线为空时 diff 一律返回空，不误报。
- 全取消勾选 = “已查看本版本”：不执行任何采集，但刷新快照（`mark_applied`），保留全部本地内容；官网下次变化会重新提示。
- **可视化进度**：所有联网等待必须有进度反馈——公告检查与更新前置拉取显示状态栏不确定进度条（动画 + 阶段文字），武将采集子进程解析 stdout `[n/N]` 显示确定进度；完成/失败自动隐藏，避免用户误以为卡死而重复点击。
- **全文比对采用 Git 风格 diff**：`src/ui/shared/rich_diff.py` 基于 `difflib.SequenceMatcher` 做行级 diff，修改块再做字符级染色；删除行浅红 + `-`，新增行浅绿 + `+`，未变化行无标记，相同前缀/后缀不染色。
